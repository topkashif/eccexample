# Design v4: CDD-based Multiplex Transport for vKeyM_MPKA Key Negotiation (IPC ECU, RH850/F1KM)

Status: DRAFT v4. Header and frame layout are frozen per SD.00136/04 (Figures 1 and 2). No DBC exists, so the
frame layout is specified by this document plus the executable reference model `keypub_ref_model.py`
(same folder). One engineer implements it.

Changes from v3:
- Key negotiation header frozen per SD.00136/04 Fig. 1: 16 bits = MUXID(1) ROUND(1) ECUID(8) GROUPID(6), in frame 0 bytes 1-2.
- **Correction 1:** Key_Header is 16 bits (start 16, length 16), not 8. SD.00136 Fig. 1/2 and the earlier MGRP_21 screenshot both show 16. The "length 8" in the typed layout is treated as a typo (confirm, Q1).
- **Correction 2:** Part9 (start 16, len 16) occupies frame bytes **1-2**, not 2-3 as in v2/v3. It matches SD.00136 Fig. 2 (last frame: key data in bytes 1-2, rest empty).
- Detailed one-person implementation plan (Section 9) replaces the activity table.
- The no-DBC situation is handled by the reference model and fixed test vectors (Section 6.3).

## 1. Purpose and scope

Carry the ECDH public-key exchange (CS.00172, P-224) for key group 2 (IPC LOCALID 3 + EVCU LOCALID 4) over
classic CAN HS, using the unmodified Vector `vKeyM_MPKA`. vKeyM sees one 64-B PDU in each direction. Two CDDs
per direction:
- **Rx:** CanIf → PduR → IpduM (demux) → PduR → **CddConcat** (concatenate 9 part PDUs) → PduR → **CddForward** (one PDU) → PduR → vKeyM.
- **Tx:** vKeyM → PduR → **CddForward** (one PDU in) → PduR → **CddConcat** (IpduM replacement: split into 9 multiplexed frames) → PduR → CanIf.

IpduM is removed from Tx (Vector IpduM TechRef 2.1.1: the Tx pathway links only to COM).

## 3. Frozen frame layout

### 3.1 Bit-order rule
Motorola signals with the DBC start bit at byte 7 (start bit 56 = bit 0 of byte 7). Each signal ends in its
least significant byte at the stated start byte, and the signal's most significant byte is the lowest-numbered
byte. Result: every field is byte-aligned, and bytes are copied in big-endian order. No bit shifting is needed.

### 3.2 Frame map (Tx MGRP_22 0x72, Rx MGRP_21 0x71, identical)

| Mux (byte 0) | Bytes 1-2 | Bytes 3-7 | Key bytes carried |
|---|---|---|---|
| 0x00 | KMSG.HDR (16 bits) | key[0..4] | 5 |
| 0x01 | key[5..6] | key[7..11] | 7 |
| 0x02 … 0x07 | key continues, 7 bytes per frame (bytes 1-7) | | 7 each |
| 0x08 | key[54..55] | 00 00 00 00 00 | 2 |

Total: 5 + 7×7 + 2 = 56 key bytes (P-224 X‖Y) over 9 frames. Every frame has DLC 8.

### 3.3 Header mapping (vKeyM header ⇄ KMSG.HDR)

```
KMSG.HDR = MUXID<<15 | ROUND<<14 | ECUID<<6 | GROUPID
frame0[1] = KMSG.HDR >> 8      frame0[2] = KMSG.HDR & 0xFF
```

| KMSG.HDR field | Tx (from vKeyM PDU) | Rx (to vKeyM PDU) |
|---|---|---|
| MUXID (1) | 1 if byte0 == 7 else 0 | byte0 = 7 if MUXID else 0 |
| ROUND (1) | byte1 bit 7 | byte1 bit 7 |
| ECUID (8) | byte1 bits 0-6 (vKeyM member id is 7 bits) | byte1 bits 0-6; reject ECUID > 127 |
| GROUPID (6) | bytes2-3 (must be ≤ 63, else reject) | byte2 = 0, byte3 = GROUPID |
| — | bytes 4-7 ignored (always 0) | bytes 4-7 = 0 |

Test vectors (generated by the reference model, see `keypub_ref_model.py`):
- IPC, group 2, negotiation: KMSG.HDR = 0x00C2, frame0 = `00 00 C2 00 01 02 03 04` (key = 00..37h).
- EVCU, group 2, confirmation: KMSG.HDR = 0x8102, frame0 = `00 81 02 A0 A1 A2 A3 A4`.
- Last frame (TV1): `08 36 37 00 00 00 00 00`.

### 3.4 Why the CAN mux and vKeyM mux differ
CAN byte 0 is the part index (0-8). vKeyM byte 0 (0/7) is the message type and is carried in KMSG.HDR.MUXID.
The CDDs translate between them. Without this, CAN mux 7 (Part8) and vKeyM mux 7 (confirmation) would collide.

## 5. Architecture

### 5.1 Data flow

```
                Tx                                              Rx
 vKeyM_MPKA  --PduR_vKeyM_MPKATransmit(64B)-->        vKeyM_MPKA_RxIndication(64B) <--
     PduR    (route VKEYM_TX -> CDDFWD_TX)                 PduR (route CDDFWD_RX -> VKEYM_RX)
 CddForward  (copy 64B, hold, confirm when done)      CddForward (rebuild 8B header, 64B PDU)
     PduR    --PduR_CddForwardTransmit(64B)-->              PduR (route CDDCAT_RX_FULL -> CDDFWD_RX)
 CddConcat   (split -> 9 frames, retry, conf)         CddConcat  (collect 9 parts, bitmap, timeout)
     PduR    --PduR_CddConcatTransmit(8B) x9-->             PduR (route IPDUM parts 0..8 -> CDDCAT_RX_k)
 CanIf_Transmit MGRP_22 0x72                           IpduM Rx (selector byte 0, 9 dynamic parts)
                                                           PduR <- CanIf Rx MGRP_21 0x71
```

### 5.2 Module responsibilities

| | CddForward | CddConcat |
|---|---|---|
| Tx | Lower layer of PduR for the vKeyM PDU. Validates length 64, copies, forwards 64 B to CddConcat over PduR, waits. On CddConcat confirmation, confirms vKeyM. | Lower layer of PduR for the 64-B PDU (IpduM replacement). Builds frame k from the map, transmits over PduR → CanIf, advances on CanIf TxConfirmation, retries, reports done/abort upward. |
| Rx | Upper layer of PduR for the reassembled PDU. Translates KMSG.HDR → 8-B vKeyM header, delivers one 64-B PDU to vKeyM. | Upper layer of PduR for the 9 part PDUs. Copies each part into its key offset, tracks bitmap, times out, hands the 58-B result (2 header + 56 key) to CddForward over PduR. |

The header translation lives in CddForward, so CddConcat only knows the CAN layout and CddForward only knows the vKeyM layout.

### 5.3 PDU inventory (EcuC)

| EcuC PDU | Length | Producer → Consumer |
|---|---|---|
| PDU_vKeyM_Tx | 64 | vKeyM → CddForward |
| PDU_CddFwd_Tx | 64 | CddForward → CddConcat |
| PDU_MGRP_22_Tx | 8 | CddConcat → CanIf |
| PDU_MGRP_21_Rx | 8 | CanIf → IpduM |
| PDU_MGRP_21_Part0 … Part8 | 8 each (Q3) | IpduM → CddConcat |
| PDU_CddCat_Rx | 58 | CddConcat → CddForward |
| PDU_vKeyM_Rx | 64 | CddForward → vKeyM |

Total: 15 EcuC PDUs, about 13 PduR routing paths (including confirmations).

## 6. Detailed design

### 6.1 CddConcat Tx (IpduM replacement)

Data: `cat_txSrc[64]` (no copy needed if CddForward keeps its buffer stable; recommended: keep the reference only), `cat_txFrame[8]`, `cat_txIdx`, `cat_txRetry`, `cat_txState`.

```
CddConcat_Transmit(PDU_CddFwd_Tx, info):
  if state != IDLE or info->SduLength != 64 -> E_NOT_OK
  src = info->SduDataPtr   (CddForward guarantees the buffer stays valid until confirmation)
  idx = 0; retry = 0; state = SEND; return E_OK     (first frame sent in the same call, see below)

SendFrame():
  build frame[idx] per Section 3 (memset 0, frame[0] = idx, header in frame 0, key bytes)
  if PduR_CddConcatTransmit(PDU_MGRP_22_Tx, frame) == E_OK -> state = WAIT_CONF, start conf timer
  else retry++ ; if retry > MAX_RETRY -> Finish(E_NOT_OK) else state = SEND (main function retries)

CddConcat_TxConfirmation(PDU_MGRP_22_Tx):     (from CanIf via PduR)
  if state != WAIT_CONF -> ignore
  idx++ ; retry = 0
  if idx == 9 -> Finish(E_OK) else SendFrame()

CddConcat_MainFunction():   (10 ms)
  if state == SEND -> SendFrame()
  if state == WAIT_CONF and conf timer > TX_CONF_TIMEOUT (e.g. 50 ms) -> retry++ ; resend same idx or Finish(E_NOT_OK)

Finish(result): state = IDLE; PduR_CddConcatTxConfirmation(PDU_CddFwd_Tx[, result])
```

Notes:
- Same CAN ID for all 9 frames, one in flight, so frame order on the bus is guaranteed.
- Sending the next frame from the TxConfirmation context gives the shortest burst (about 9 × 0.25 ms at 500 kbit/s). If the CanIf Tx confirmation runs in ISR context, move SendFrame to the main function instead (one frame per 10 ms, about 90 ms per message). Both are well inside 5 s.
- Resending a frame after a CanIf confirmation timeout is safe because the receiver drops duplicates.

### 6.2 CddForward Tx

```
CddForward_Transmit(PDU_vKeyM_Tx, info):
  if busy or info->SduLength != 64 -> E_NOT_OK (DET)
  memcpy(fwd_txBuf, info->SduDataPtr, 64)    (vKeyM's buffer is on its stack)
  validate header: byte0 in {0,7}, bytes2-3 <= 63, member <= 127 -> else E_NOT_OK (DET)
  busy = TRUE
  return PduR_CddForwardTransmit(PDU_CddFwd_Tx, {fwd_txBuf, 64})   (if E_NOT_OK: busy = FALSE)

CddForward_TxConfirmation(PDU_CddFwd_Tx[, result]):     (from CddConcat via PduR)
  busy = FALSE
  if result != E_OK -> Dem/DET KEYPUB_TX_FAILED
  PduR_CddForwardTxConfirmation(PDU_vKeyM_Tx)   -> vKeyM_MPKA_TxConfirmation   (always, see 6.6)
```

The header-to-KMSG translation runs in CddConcat when it builds frame 0, using the 64-B buffer from CddForward. Equivalently, CddForward can pre-translate. Pick one place and test it there (proposal: a shared `KeyPub_Hdr` helper in a common header that both CDDs include).

### 6.3 CddConcat Rx (reassembly)

Data per slot (2 slots: negotiation and confirmation, because the peer's confirmation can arrive while the negotiation slot is in use):
`buf[58]` (header 2 + key 56), `mask` (uint16), `timer` (uint16, ms), `state`.

Part 0 is not guaranteed to arrive first, so the slot type is unknown until part 0 arrives. Rule:
- Keep one **staging** slot for parts 1-8 that arrive before part 0. When part 0 arrives, MUXID selects the final slot and staging is merged.
- In practice IpduM delivers frames in bus order and the sender sends 0..8 in order, so staging is a robustness path, not the normal path.

```
CddConcat_RxIndication(PDU_MGRP_21_Part_k, info):
  k = PduId - PART0 ; if k > 8 -> drop
  if k == 0: hdr = info[1]<<8 | info[2]; slot = MUXID(hdr) ? CONF : NEG
             if slot busy and timer < RX_TIMEOUT and mask has bit0 -> new message restarts slot (clear)
             store hdr
  copy key bytes of part k (Section 3.2) into slot.buf
  if bit k already set -> drop (duplicate)
  set bit k ; timer = 0
  if mask == 0x1FF -> PduR_CddConcatRxIndication(PDU_CddCat_Rx, {slot.buf, 58}); clear slot

CddConcat_MainFunction(): for each active slot timer += 10; if > RX_TIMEOUT (500 ms) -> clear, DET/DEM
```

### 6.4 IpduM Rx and part PDUs (Q3)
IpduM delivers each dynamic part as an 8-byte PDU with the same byte positions as the CAN frame (standard IpduM
behaviour for dynamic parts that start at byte 0 and include the selector). The design assumes that. If the
generated config gives different part lengths, only the per-part offset table changes (one const table).
Configuration: selector field position bit 0, length 8; nine dynamic parts with RxSelectorValue 0..8.

### 6.5 CddForward Rx

```
CddForward_RxIndication(PDU_CddCat_Rx, info):     (58 B)
  hdr = info[0]<<8 | info[1]
  if ECUID(hdr) > 127 -> drop, DET
  fwd_rxBuf[0] = MUXID ? 7 : 0 ; fwd_rxBuf[1] = ROUND<<7 | ECUID ; [2] = 0 ; [3] = GROUPID ; [4..7] = 0
  memcpy(&fwd_rxBuf[8], &info[2], 56)
  PduR_CddForwardRxIndication(PDU_vKeyM_Rx, {fwd_rxBuf, 64})
```

vKeyM then checks member against PROXI and group id itself (existing behaviour, unauthorized sender handling).

### 6.6 Abort behaviour (recommendation)

Verified in vKeyM code: `TransmissionBlocked` is cleared only by `vKeyM_MPKA_TxConfirmation` or init. The
negotiation timeout does not clear it.

| Option | Result |
|---|---|
| A. Confirm after bounded retries + DEM (**recommended**) | vKeyM stays usable. The negotiation fails cleanly by the 5 s timeout on both ECUs, which raises the standard DTC. A later retrigger (RID $2002) works without reset. |
| B. Never confirm on abort | vKeyM blocks all transmits until reset. Not acceptable. |
| C. CDD calls `vKeyM_MPKA_ClearTransmissionBlockFlag()` | Accurate but uses an internal vKeyM function. Only with Vector's written agreement. |

Recommendation: **Option A**. MAX_RETRY = 3 per frame. TX_CONF_TIMEOUT = 50 ms per frame. Worst case abort
(9 frames × 4 attempts × 50 ms) is 1.8 s, which still lets vKeyM's 5 s timer expire cleanly. Raise a CDD DEM event
(`DEM_KEYPUB_TX_FAILED`) so the cause is visible beside vKeyM's timeout DTC. Ask Vector to confirm (one email).

### 6.7 Memory (P-224, CDD only, estimates to confirm from the map file)

| Item | RAM |
|---|---|
| CddForward Tx copy | 64 B |
| CddForward Rx output | 64 B |
| CddConcat Tx frame + state | ~12 B |
| CddConcat Rx 3 slots (NEG, CONF, staging) × (58 + 6) | ~192 B |
| **Total** | **~330 B** |
| Reduced variant (no staging, 2 slots) | ~270 B |

ROM: CddConcat ~1.5–2 KB, CddForward ~0.6–1 KB, const frame table ~40 B. IpduM Tx code for this message is removed;
the saving depends on whether other IpduM Tx pathways remain. The SecLib_Ecc backend (mbedtls ECP + bignum) is
not included and will dominate RAM, ROM and stack. Measure it in WP2.

CPU: per frame < 5 µs of copying. Negligible.

### 6.8 Error handling

| Event | Module | Action |
|---|---|---|
| Tx length / header invalid | CddForward | E_NOT_OK, DET |
| CanIf E_NOT_OK or no confirmation | CddConcat | retry 3, then abort (6.6) |
| Rx part index > 8 | CddConcat | drop, DET |
| Rx duplicate | CddConcat | drop |
| Rx timeout | CddConcat | clear slot, DET (optional DEM) |
| ECUID > 127 | CddForward | drop, DET |
| Unknown sender / group | vKeyM | existing behaviour |

### 6.9 Concurrency and context
- vKeyM is single-flight on Tx, so the CDDs need one Tx context.
- CanIf Rx indication context: check `CanIfRxIndication` call context (ISR or task). If ISR, CddConcat RxIndication must be short (it is, copy only), and the hand-off to vKeyM must happen in task context. vKeyM RxIndication runs in the caller context, so prefer polling-mode CAN Rx, or defer the CddForward → vKeyM call to the CddForward main function.
- Protect slot state with an exclusive area (`SchM_Enter_CddConcat_...`) if Rx indication and main function run on different tasks or priority levels.

## 7. Sequences

Tx (normal):
```
vKeyM -> PduR -> CddForward_Transmit (copy) -> PduR -> CddConcat_Transmit
  CddConcat: frame0 -> PduR -> CanIf_Transmit(0x72) ... CanIf -> PduR -> CddConcat_TxConfirmation
  ... frames 1..8 ...
  CddConcat -> PduR -> CddForward_TxConfirmation -> PduR -> vKeyM_MPKA_TxConfirmation
```

Rx (normal):
```
CanIf(0x71) -> PduR -> IpduM -> PduR -> CddConcat_RxIndication(part k) x9
  -> PduR -> CddForward_RxIndication(58 B) -> PduR -> vKeyM_MPKA_RxIndication(64 B)
```

## 9. Implementation plan for one engineer

Assumptions: one engineer, familiar with DaVinci Configurator and the build, with target hardware, CANoe (or
equivalent) and access to the EVCU or a simulated EVCU. Durations are working days and estimates.

### WP0 — Setup and baseline (2 days)
1. Branch the project. Build the current baseline and record the map file (ROM/RAM/stack) as the reference.
2. Confirm toolchain: Cdd generator (`Cdd_AsrCddCfg5.jar`) is in the DaVinci installation; MemMap template available.
3. Set up a CANoe configuration with 0x71/0x72 (raw frames, no DBC needed) and a CAPL node to replay test vectors.
Exit: baseline builds and runs; CANoe sees the bus.

### WP1 — Executable spec and test vectors (1 day)
1. Review `keypub_ref_model.py` against Section 3 (done once, it already self-tests 2000 round trips).
2. Generate vectors for: IPC negotiation, IPC confirmation, EVCU negotiation, EVCU confirmation, boundary values (ECUID 127, GROUPID 63).
3. Save them as a C header `KeyPub_TestVectors.h` for unit tests and as a CAPL include for CANoe.
Exit: vectors frozen and reviewed.

### WP2 — Crypto readiness, early (3 days, runs before CDD work to remove the biggest risk)
1. Integrate SecLib_Ecc into the build (already referenced by `Crypto_30_CryWrapper_Hw.c`). Call `SecLib_EccInit` in the init path.
2. Run the SecLib_Ecc self-test on target.
3. Measure on RH850/F1KM: keygen time, ECDH time (REQ 5.8.4 < 1.5 s), KDF time; stack peak; map-file ROM/RAM.
4. Configure Csm/CryIf keys for vKeyM (KeyExchange key with PRIVKEY 28, OWNPUBKEY 56, SHAREDVALUE 56 or 28, KDF key) per vKeyM TechRef 5.5/5.6.
Exit: measured numbers. If ECDH > 1.5 s, stop and escalate before continuing.

### WP3 — EcuC, PduR, CanIf, IpduM configuration (3 days)
1. Create the 15 EcuC PDUs (Section 5.3).
2. CanIf: Tx PDU 0x72, Rx PDU 0x71 (Section 8). Remove or detach any existing IpduM Tx pathway for MGRP_22. Check that no other PDU uses that IpduM Tx path.
3. IpduM: Rx pathway MGRP_21 with 9 dynamic parts.
4. Create CddForward and CddConcat module configurations (two Cdd instances) with their contributions.
5. PduR: all routing paths and BSW module entries. Check every path in the PDU Graph.
6. vKeyM: Rx/Tx PDU refs, curve, group 2, members 3 and 4, timeouts.
7. Generate. Fix validation errors.
Exit: generation clean, `Cdd_Cbk.h` / `PduR_<Cdd>.h` prototypes generated for both CDDs.

### WP4 — Common helper and CddConcat (5 days)
1. `KeyPub_Common.h/.c`: frame table (const), header pack/unpack helpers (Section 3.3), constants.
2. `CddConcat.c`: Init, Transmit, TxConfirmation, RxIndication, MainFunction, state machines (6.1, 6.3); MemMap sections; DET hooks.
3. Unit tests on host (gcc + a small test runner or the project's unit-test tool) using `KeyPub_TestVectors.h`:
   split = vectors; out-of-order and duplicate reassembly; timeout; retry and abort paths; invalid part index.
Exit: all unit tests pass; the C output matches the Python vectors byte for byte.

### WP5 — CddForward (3 days)
1. `CddForward.c`: Init, Transmit (copy + validate), TxConfirmation (always confirm vKeyM, DEM on failure), RxIndication (header rebuild), MainFunction (if deferred delivery is chosen, 6.9).
2. Unit tests: header translation both ways, invalid headers, length checks, abort propagation.
Exit: unit tests pass.

### WP6 — Integration build and static checks (2 days)
1. Add sources to the makefiles (`*_rules.mak` pattern as for other modules), OS task mapping for main functions, exclusive areas.
2. Build, run MISRA/QAC (project rules), fix findings.
3. Map file: compare with WP0 baseline, record CDD and ECC deltas.
Exit: warnings-free build, MISRA report, memory report.

### WP7 — Target tests with CANoe (4 days)
1. Tx: trigger RID $2002 on IPC; capture 0x72; compare the 9 frames with the expected header and layout (key varies, header and structure fixed).
2. Rx: CAPL replays EVCU vectors on 0x71; check vKeyM receives 64 B (debugger breakpoint on `vKeyM_MPKA_RxIndication`, SduLength 64, header bytes).
3. Fault injection: drop a frame, duplicate frames, reorder, delay > 500 ms, bus-off during Tx, no ACK (CAN disconnected) to exercise the abort path and confirm vKeyM is not blocked afterwards.
4. Timing: full negotiation time IPC side vs 5 s.
Exit: all cases pass; abort case shows vKeyM recovery without reset.

### WP8 — End-to-end with EVCU (3 days, depends on EVCU availability)
1. Real key negotiation IPC ↔ EVCU for group 2. Check both ECUs report success and the derived key matches (compare by a SecOC-protected message, e.g. HV_BATT 24-bit MAC verifies).
2. Repeat 50+ negotiations; power cycle in between; renegotiation (CS.00172 REQ 5.8.1 behaviour is in vKeyM).
Exit: repeated successful negotiations; SecOC verification passes with the negotiated key.

### WP9 — Documentation and review (2 days)
1. Update this design to "as built", unit-test report, integration-test report, memory/timing report, deviation note (ECC software, REQ 5.6.1/5.8.8).
