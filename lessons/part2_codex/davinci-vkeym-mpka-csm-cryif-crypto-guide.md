# DaVinci configuration guide: vKeyM_MPKA CSM key references

## Purpose and current limits

This guide describes how to configure the DaVinci ECUC objects so the `vKeyM_MPKA` references for a two-ECU ECDH negotiation resolve to the intended key objects. The IPC use case in this workspace is group 2, local member 3, remote EVCU member 4, P-224/secp224r1, and a SecOC AES-128 message-group key.

The workspace PC currently has neither DaVinci Configurator nor the target compiler. This is a configuration plan, not a generated ECUC export or proof of successful generation, compilation, linking, or target behavior. The workspace contains BSWMD schemas and vendor/specification documents, but no active IPC project ECUC export was included in this review. Resolve project-specific IDs, exact release parameter choices, and symbolic paths in the IPC build environment.

You report that the target uses a project-owned CSM/CryIf replacement and does not link the Vector runtimes. In this workspace, `security/` contains SecurityLib and a specific SecOC MAC adapter, but inspection did not find a complete CSM/CryIf-compatible key API implementation. DaVinci containers can still be used as design-time definitions and as a source of generated/symbolic key identities, provided the custom runtime consumes or faithfully mirrors their mapping. Configuring a container does not install its runtime implementation. The runtime facade must resolve MPKA's CSM key handles and dispatch each service into the selected project key store/provider. The existing `secoc_securitylib_csm_wrapper.c` is a SecOC MAC adapter; it does not implement MPKA's key-management API family.

## Project-specific addendum: confirmed choices

This addendum applies your answers to the generic steps below.

- **CSM/CryIf definitions:** use the AUTOSAR-standard CSM and CryIf module definitions already added to DaVinci. The custom implementations own the `Csm_*` and any `CryIf_*` symbols called by MPKA. ECUC data supplies names, IDs, and references; it does not implement those APIs.
- **Crypto definition:** continue using the Vector `Crypto_30_CryWrapper` module definition/configuration. Its BSWMD refines `/AUTOSAR/EcucDefs/Crypto`, so standard CSM/CryIf references to `CryptoKey` should resolve to the wrapper's configured Crypto keys when the matching refined definition is loaded. You report that the key-management implementation is present under `component/Crypto_30_CryWrapper/Implementation`; verify the active build manifest selects those sources and the configured public APIs/key storage are enabled. Folder presence alone does not establish that they are linked. Verify this in DaVinci; if the `CryIfKeyRef` chooser cannot see the wrapper's keys, fix the module-definition/package mismatch rather than entering a numeric ID manually.
- **Runtime map:** map each configured `CsmKeyId` to its `CryIfKeyId`, then to the intended `CryptoKeyId` (or the matching project-owned descriptor if custom CryIf bypasses Vector dispatch). Preserve the IDs generated by this DaVinci project in the custom code/table.
- **Shared secret:** set `CddKeyNegotiationSharedValueLengthType = VKEYM_MPKA_SHARED_VALUE_LENGTH_X_AND_Y`. For P-224, configure `CRYPTO_KE_KEYEXCHANGE_SHAREDVALUE` to **56 bytes** and the KDF `PASSWORD` element to **56 bytes**. This matches your CS.00172 REQ 5.7.2 interpretation: `Z = x || y`, big endian. Verify the wrapper/provider API really returns and stores both 28-byte coordinates in that order; do not assume a generic ECDH operation's usual x-coordinate output matches this MPKA contract. Both ECUs must use the same curve, length, byte order, and KDF inputs.
- **Key element IDs:** use standard IDs from the exact CSM/Crypto headers; obtain Vector custom `CUSTOM_KEYEXCHANGE_*` IDs from the installed MPKA/Crypto template or generated headers. Do not infer custom IDs from labels. The checked-in public CSM types identify `PRIVKEY=9`, `OWNPUBKEY=10`, `SHAREDVALUE=1`, `KEYEXCHANGE_ALGORITHM=12`, `KEYDERIVATION_PASSWORD=1`, `KEYDERIVATION_SALT=13`, and the MAC key element as ID 1. These are element IDs, not CSM key IDs.
- **SHE configuration:** retain existing SHE keys/types for SHE services. Do not point MPKA's group-exchange or KDF-input references at `SheNvmKey` or `SheRamKey`: those are virtual/slot-backed, and the configured SHE RAM element is 16 bytes while MPKA needs 56-byte software ECDH state. Create distinct, non-virtual CryptoKeyElements and CryptoKeyTypes for the MPKA software exchange/KDF objects. If your approved post-finalization design loads the 16-byte SecOC key into ICUSE `RAM_KEY`, keep it as a separate activation destination.

The exchange key type contains the exchange rows; the minimum KDF-input type used by the checked-in `Crypto_30_CryWrapper_Hw_KeyDerive` contains PASSWORD and SALT; the MAC type contains the MAC key row. The temporary and final key objects both use that same 16-byte MAC type. However, the checked-in public `Crypto_30_CryWrapper_KeyDerive` header says its input key also contains `CRYPTO_KE_KEYDERIVATION_ALGORITHM` and `CRYPTO_KE_CUSTOM_KEYDERIVATION_LABEL`, while the checked-in hardware implementation reads only PASSWORD and SALT and hard-codes X9.63/SHA-256. Resolve this API/header/implementation difference against the exact wrapper version in the IPC build. Add those non-secret elements with exact IDs/values if its generated template or active public API requires them; do not guess IDs or rely on a contradictory contract. If a size is larger than the bytes actually set/copied/cleared, enable partial access for that element and verify exact CryWrapper behavior. With the selected exact 56-byte values, no partial access is needed for shared value or PASSWORD.

Set access/persistence deliberately:

- Public points and MPKA metadata need the read/write access used by the group workflow. Provider APIs should not require exposing the private scalar/shared secret to application code.
- MPKA explicitly calls `Csm_KeyElementSet` to clear `PRIVKEY`, `SHAREDVALUE`, `PASSWORD`, and MAC element 1, and calls `Csm_KeyElementCopy`/`Csm_KeyCopy`; configure write and internal-copy permissions so those operations succeed. For secret elements, deny plaintext `KeyElementGet` where possible. Use `RA_INTERNAL_COPY`/`WA_INTERNAL_COPY` only if the custom CSM/Crypto copy path supports those modes while still permitting MPKA's explicit zeroization writes.
- The MPKA Technical Reference says the KDF-input key need not be persisted and the temporary/final derived message-group keys shall be persisted; it does not require persistence of the negotiation-group exchange key. Set exchange and KDF-input elements non-persistent to keep ephemeral private/shared values out of NvM. Set the dedicated MAC-key element used by the MPKA temporary/final objects persistent. If any product requirement needs negotiation resume across reset, assess persistence of exchange state separately.
- Since the temporary/final MPKA MAC element is persistent, configure `CryptoGeneral/CryptoNvMBlockDescriptor` and enable `CryptoNvMEnableSetRamBlockStatus` consistently with the active NvM design. Software Crypto persistence is not SHE protection. The derived final key is software data until an explicit load/activation flow moves it to ICUSE `RAM_KEY`.
- `ReadAccess=RA_ALLOWED` on the final key is needed only if an approved adapter reads plaintext key bytes into CPU memory to load ICUSE. If SecOC uses an internal/job path, prefer denying plaintext read and validate that path.

For `CryptoDriverObjects/CryptoDriverObject`, an object has `CryptoDriverObjectId`, `CryptoDriverObjectQueueSize`, and one or more `CryptoPrimitiveRef` entries in this wrapper schema. Preserve the current SHE/job driver-object configuration. Do not add an ECDH or KDF `CryptoPrimitive` only for MPKA: its checked-in source uses direct key-ID operations. Add/configure a `CryptoPrimitive` and bind it to a driver object only if a real job-based client in this ECU uses that primitive. The wrapper BSWMD fixes its queue size to 1 and states the driver does not support queued jobs.

### Keep SHE-specific objects separate

In the checked-in CryWrapper preconfiguration, `SheNvmKey` is a 64-byte SHE-backed virtual element with persistence/encrypted-write semantics, and `SheRamKey` is a 16-byte SHE-backed virtual element that is not persistent. They are for SHE operations, not the 56-byte P-224 ECDH state, scalar, or KDF password. Keep them for SHE services. Create ordinary, non-virtual software key elements for MPKA. If required by the product, load the committed 16-byte final key into SHE `RAM_KEY` after MPKA finalization as a separate step.

## Short answer

Build this key-reference chain bottom-up for every MPKA CSM key:

```text
vKeyM_MPKA CDD key reference
    -> CsmKey (unique CsmKeyId)
        -> CsmKeyRef
            -> CryIfKey (unique CryIfKeyId)
                -> CryIfKeyRef
                    -> CryptoKey (unique CryptoKeyId)
                        -> CryptoKeyType
                            -> CryptoKeyElements
```

Then map the generated `CsmKeyId` handles into the custom CSM facade's descriptor table. Keep CSM key IDs, CryIf key IDs, Crypto key IDs, MPKA group/member/message-group IDs, SecOC job IDs, and SecOC Data IDs as separate namespaces. Equal numeric values do not imply a valid mapping.

The checked-in `vKeyM_MPKA_CryptoStateMachine.c` calls `Csm_KeyExchangeCalcPubVal`, `Csm_KeyExchangeCalcSecret`, `Csm_KeyDerive`, `Csm_KeyElementSet`, `Csm_KeyElementCopy`, `Csm_KeyCopy`, and `Csm_KeySetValid` with CSM key IDs. These are direct key-ID services. They use the CSM key-to-CryIf key-to-Crypto key chain above; they do not get a route from `CsmJob`, `CsmQueue`, or `CryIfChannel`.

If another client such as SecOC uses a job-based `Csm_MacVerify`/`Csm_MacGenerate` API, configure that job path separately:

```text
SecOC job reference -> CsmJob -> CsmPrimitive + Csm key reference + CsmQueue
    -> CsmChannelRef -> CryIfChannel -> CryptoDriverObject
```

Bind the SecOC MAC job to the final `CddMsgGrpKey`, not to the negotiation-group key or temporary key. Configure the required algorithm/mode, MAC length, synchronous/asynchronous behavior, callback, queue and channel for the active SecOC/CSM version. If the custom runtime owns MAC dispatch, mirror those semantics in its explicit job registry; a numeric job ID alone does not perform routing.

## 8. Connect the generated IDs to the custom CSM/CryIf implementation

This step is the key difference between a working declarative configuration and a usable target. Since the Vector CSM/CryIf runtime sources are omitted, implement or confirm a project-owned facade with these responsibilities:

1. **Handle resolution:** map every generated CsmKeyId to one descriptor containing its CryIf/Crypto identity, key type, element table, access policy, storage/lifetime, and provider selection.
2. **Reference consistency:** at initialization (or in a generated static table), reject missing, duplicate, out-of-range, or mismatched CSM→CryIf→Crypto references.
3. **Direct key APIs:** implement the exact subset MPKA calls, including length/permission/validity/error semantics for element set/copy, whole-key copy, key valid, public-value calculation, shared-secret calculation, and key derive.
4. **Provider dispatch:** call the Crypto wrapper's supported public key API/key table when it is in the build. Its internal `Hw_*` routines are not a CSM/CryIf callback registration point. If a custom descriptor dispatches directly to a provider, explicitly take responsibility for the wrapper checks, serialization, and lifecycle that would otherwise be provided at the public boundary.
5. **Key storage semantics:** ensure the CSM-facing key descriptors and Crypto wrapper key-element storage refer to the same values. Do not maintain a separate custom key buffer that the ECC/KDF provider cannot see.
6. **Validity and errors:** preserve MPKA's write-then-`Csm_KeySetValid` sequence, only mark data valid after successful writes, and propagate failures. The current workspace notes identify validity behavior as a boundary to verify against the exact wrapper release.
7. **Single symbol owner:** inspect the IPC link/build manifest for existing `Csm_*` and `CryIf_*` exports before adding project-owned ones. There must be exactly one implementation per global API symbol.

The existing `security/source/crypto_lib/secoc_securitylib_csm_wrapper.c` handles a specific MAC job compatibility route. It does not provide `Csm_KeyElementSet`, key-ID mappings, ECDH calls, or the complete CSM key service family needed by MPKA. Since the checked-in MPKA component calls `Csm_*` symbols directly, the IPC build must either provide a compatible API facade under the exact expected interfaces or use an approved integration seam that changes those calls. If neither exists, the key references may be syntactically configurable but MPKA cannot use them at runtime.

## 9. DaVinci generation and review on the IPC build PC

When the configurator is available:

1. Open the active IPC DaVinci project and ensure it loads the correct BSW package/BSWMD versions and ECU extract.
2. Configure/edit the Crypto key elements, key types, and keys; then CryIf keys/module mapping; then CSM keys; then the vKeyM_MPKA CDD key references. DaVinci can resolve the references only when the target containers and schemas are present.
3. Run DaVinci consistency checks and resolve unresolved/wrong-type references. Confirm every MPKA key reference resolves to a `CsmKey`, every CsmKey to one `CryIfKey`, and every CryIf key to the intended `CryptoKey`.
4. Generate/export ECUC and configuration code according to the project's existing build workflow. Preserve the generated CSM key IDs in the custom facade mapping and confirm the active MPKA generated code uses those same IDs.
5. Diff the generated artifacts against the reviewed mapping table. Check custom element numeric IDs and actual generated key-element capacities in generated headers/config.
6. Audit the build manifest/link map to verify the custom CSM/CryIf runtime is the sole owner of those API symbols and that the Crypto wrapper/provider implementation and SecurityLib sources are present.
7. Compile/link with the IPC GHS toolchain, then validate on the RH850 target. Only the build-PC generation/compile and target tests can establish those outcomes; this current PC cannot do so.

## 10. Validation sequence after configuration

1. **Static reference audit:** trace all four CDD references through CsmKey, CryIfKey, CryptoKey, CryptoKeyType, and every element ID/size.
2. **Provider API audit:** confirm both ECDH direct operations and X9.63/SHA-256 KDF are implemented in the selected provider, with the correct P-224 encoding and RNG initialization order.
3. **Two-ECU exchange:** on bench IPC/EVCU devices, run group 2 negotiation and compare the resulting 16-byte derived key through a protected test method; never log or transmit the secret for diagnostics.
4. **Key lifecycle:** verify CSM validity transitions, copy from temporary to final key, clearing of private/shared/PASSWORD material, and expected reset/persistence behavior.
5. **SecOC:** verify the configured job/adapter uses the final key, reports valid MAC vs mismatch distinctly, and follows the accepted ICUS RAM_KEY ownership policy if the SecurityLib adapter loads it into volatile ICUS RAM.
6. **Failure tests:** exercise unknown key/job IDs, incorrect element sizes, invalid peer points, failed KDF/copy, uninitialized provider/RNG, and callback errors. Fail closed and ensure an incomplete or stale final key is not activated.

## Common configuration mistakes

- Configuring only a CsmJob for MPKA's key-ID calls: those direct calls need CSM keys and references.
- Pointing `CddKeyNegotiationGroupKeyRef` at the final SecOC key: the group key is the ECDH state object; final MAC key is a distinct message-group object.
- Using the temporary key in SecOC: only the committed final `CddMsgGrpKey` is the MAC key.
- Assuming CSM, CryIf, and Crypto IDs share one numeric domain.
- Creating DaVinci CSM/CryIf containers and assuming that creates or substitutes the missing runtime source implementation.
- Treating `Crypto_30_CryWrapper_Hw_*` as callbacks called by custom CSM/CryIf without explicitly routing to them through wrapper APIs/provider registration.
- Treating ICUSE AES/CMAC/PRNG capability as hardware ECDH. The workspace ECDH implementation is mbedTLS software ECC.
- Setting the P-224 shared value to 28 B despite the confirmed `X||Y` REQ 5.7.2 contract; use 56 B for both `SHAREDVALUE` and KDF `PASSWORD`.
- Populating key elements with seed secrets or making ephemeral material readable just to simplify inspection.
