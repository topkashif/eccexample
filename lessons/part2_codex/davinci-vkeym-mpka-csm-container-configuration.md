# DaVinci configuration: CSM containers for vKeyM_MPKA

## Scope and assumptions

This document covers AUTOSAR CSM ECUC containers needed to give vKeyM_MPKA its CSM key handles. The IPC project has loaded CSM and CryIf module definitions from AUTOSAR standard definitions, not the Vector CSM/CryIf runtime package. Project-owned code will own every `Csm_*` (and any `CryIf_*`) symbol MPKA calls. The ECUC configuration supplies symbolic names, IDs, and references; it does not implement those functions.

The CSM key-reference chain for this flow is:

```text
vKeyM_MPKA CDD reference -> CsmKey -> CsmKeyRef -> CryIfKey -> CryIfKeyRef -> CryptoKey
```

Configure the Crypto and CryIf targets first so DaVinci can resolve CSM references. This PC has no DaVinci Configurator or target compiler, so this document is a plan and checklist, not generated ECUC or compile evidence. Parameter names may vary with the active standard release; use the exact schema loaded in the IPC project and do not import unavailable Vector-only fields.

## CSM key objects required

Create four `CsmKey` objects, one for each logical key role. The checked-in CSM BSWMD path is `/AUTOSAR/EcucDefs/Csm/CsmKeys/CsmKey`; use the active standard definition's equivalent path.

| Suggested CsmKey short name | Role | Required downstream object | vKeyM_MPKA reference |
|---|---|---|---|
| `CsmKey_MPKA_G2_Exchange` | Negotiation group ECDH state | CryIf exchange key → Crypto exchange key | `CddKeyNegotiationGroupKeyRef` |
| `CsmKey_MPKA_G2_KdfInput` | Shared value/password plus salt | CryIf KDF-input key → Crypto KDF-input key | `CddMsgGrpKDFInputKey` |
| `CsmKey_MPKA_G2_TmpMac` | Temporary 16-byte derived key | CryIf temporary key → Crypto temporary key | `CddMsgGrpTmpKey` |
| `CsmKey_MPKA_G2_FinalMac` | Committed 16-byte SecOC key | CryIf final key → Crypto final key | `CddMsgGrpKey` |

The CDD references target CSM keys, not Crypto keys. Do not point the group reference at the final SecOC key; the exchange state and final MAC key have different lifecycles.

## Configure `CsmKeys/CsmKey`

For every CsmKey, configure the mandatory key handle and symbolic reference fields:

| Field | Setting |
|---|---|
| Container short name | Unique, descriptive name from the table above |
| `CsmKeyId` | Unique CSM ID allocated/generated by this IPC project; record it in the custom CSM registry |
| `CsmKeyUsePort` | `false` for MPKA's direct CSM BSW API calls; enable only if an RTE key port is separately required |
| `CsmKeyRef` | Symbolic reference to the matching `CryIfKey` |
| `CsmKeySwcInterfaceVersion` (if present) | Relevant to a generated SWC/RTE key interface; preserve a release-compatible value if present even when not used, and do not use it as a substitute for API compatibility work |

`CsmKeyRef` should resolve through the AUTOSAR CryIf key container. The checked-in local schema describes the underlying chain as CSM key → CryIf key → CryptoKey. Keep all IDs separate: equal numeric values across CSM, CryIf and Crypto namespaces are not a mapping.

Maintain an IPC-owned mapping table. Fill IDs only after DaVinci generates/allocates them:

| CSM symbolic key | CsmKeyId | CryIf key / CryIfKeyId | Crypto key / CryptoKeyId | Intended layout |
|---|---:|---|---|---|
| Exchange | from active project | from active project | from active project | P-224 exchange key |
| KDF input | from active project | from active project | from active project | PASSWORD 56 B + SecOC SALT 1 B |
| Temporary MAC | from active project | from active project | from active project | 16-byte AES-128 key |
| Final MAC | from active project | from active project | from active project | 16-byte AES-128 key |

Feed the generated `CsmKeyId` values to the custom CSM implementation or generated registry. Do not copy IDs from another ECU variant, module release or illustrative example.

## Configure `CsmGeneral`

Use the active standard schema for available general options. The checked-in CSM BSWMD includes these fields:

| Option | Guidance |
|---|---|
| `CsmDevErrorDetect` | Keep enabled during development when project diagnostics permit; use the project's production policy. |
| `CsmVersionInfoApi` | Enable only if the project uses `Csm_GetVersionInfo`. |
| `CsmSafeBswChecks` | Set according to safety partition/ASIL requirements if exposed by the active definition. |
| `CsmMainFunctionPeriod` | Preserve/set according to scheduled CSM job processing; direct MPKA key calls are synchronous in the checked-in source. |
| `CsmUseDeprecated` | Keep false unless the integration explicitly requires a deprecated interface. |
| `CsmAsymPrivateKeyMaxLength`, `CsmAsymPublicKeyMaxLength`, `CsmSymKeyMaxLength` | The checked-in Vector BSWMD describes these maxima as unsupported/not used. Do not tune them expecting them to define Crypto key-element capacity; element sizes are configured in Crypto. |

The table summarizes the local schema only; if AUTOSAR-standard module definitions in the IPC project expose a different set, follow those definitions and preserve the project baseline.

## MPKA uses direct key-management APIs

The checked-in `vKeyM_MPKA_CryptoStateMachine.c` directly calls the CSM key-ID APIs below:

- `Csm_KeyExchangeCalcPubVal`
- `Csm_KeyExchangeCalcSecret`
- `Csm_KeyDerive`
- `Csm_KeyElementSet`
- `Csm_KeyElementCopy`
- `Csm_KeyCopy`
- `Csm_KeySetValid`

These calls require usable CsmKey handles and custom runtime dispatch to the corresponding CryIf/Crypto key data. They do **not** require a `CsmJob`, `CsmPrimitive`, `CsmQueue` or `CryIfChannel` merely to resolve the key IDs. Do not create a dummy job as a substitute for implementing the direct key APIs.

The custom CSM implementation must implement the API subset MPKA calls with compatible parameter, return, validity, permission, size and error semantics. It must dispatch each CsmKeyId through the generated CsmKeyRef/CryIfKeyRef relationship or an explicit registry that mirrors it. CSM containers alone do not provide runtime services. Link exactly one owner for each global `Csm_*` symbol.

## Add jobs, queues and primitives only for job clients

If SecOC or another client calls a job API such as `Csm_MacGenerate` or `Csm_MacVerify`, configure that job path independently of the MPKA CDD key references. The common relationship is:

```text
job client -> CsmJob -> CsmPrimitive + final CsmKey + CsmQueue
           -> CryIfChannel -> CryptoDriverObject/CryptoPrimitive
```

In the active CSM definition, configure the job's `CsmJobId`, `CsmJobKeyRef` (the final message-group key for SecOC), `CsmJobPrimitiveRef`, `CsmJobQueueRef`, required priority/callback and interface options. The queue references a `CsmChannelRef`; its CryIf channel maps to the Crypto driver object. Configure algorithm/mode/length and synchronous/asynchronous behavior from the active SecOC/CSM interfaces. The checked-in CryWrapper driver object has queue size 1 and states that queued jobs are unsupported; preserve those package constraints.

If SecOC MAC operations are instead owned by the custom adapter/runtime without a CSM job, mirror that integration's key selection in its registry and point it at the final key. Do not accidentally bind the MAC consumer to the negotiation key or temporary key.

## Map the four MPKA references

After the four CsmKeys exist, set these CDD references in the active `vKeyM_MPKA` configuration:

1. `CddKeyNegotiationGroupKeyRef` → `CsmKey_MPKA_G2_Exchange`.
2. `CddMsgGrpKDFInputKey` → `CsmKey_MPKA_G2_KdfInput`.
3. `CddMsgGrpTmpKey` → `CsmKey_MPKA_G2_TmpMac`.
4. `CddMsgGrpKey` → `CsmKey_MPKA_G2_FinalMac`.

For the SecOC message group, leave `CddMsgGrpTmpKeyMacSec` unset unless an enabled MACsec group uses it. Verify the target-type filters in DaVinci show CsmKey for each reference.

## Custom CSM integration requirements

The facade needs to:

1. Resolve every generated CsmKeyId to one descriptor with matching CryIf/Crypto identity, element layout, storage, access policy and provider.
2. Forward or implement the seven direct APIs listed above; preserve MPKA's set/copy/derive/key-valid order and propagate all errors.
3. Ensure CSM key objects and wrapper key storage refer to the same actual data. Avoid a separate custom buffer that is invisible to the Crypto wrapper.
4. Support the expected P-224 provider behavior: ECDH runs in software mbedTLS, produces 56-byte big-endian `x||y`, and uses the established ICUSE RNG bridge. Do not describe this as ICUSE hardware ECC.
5. Ensure generated CSM IDs and the custom CSM registry are synchronized after every DaVinci regeneration.
6. Verify the build manifest/link map contains one and only one implementation of each API symbol.

## Generation review checklist

1. Confirm every `CsmKeyRef` resolves to the intended CryIfKey and every CDD reference resolves to the intended CsmKey.
2. Confirm `CsmKeyUsePort=false` for these direct MPKA references unless the project has a separately documented RTE key-port need.
3. Review generated IDs against the CSM/CryIf/Crypto mapping table; check duplicates and wrong role assignments.
4. Review `CsmGeneral` against the active AUTOSAR schema and the project's job scheduling/diagnostic baseline.
5. If any job clients exist, validate their job → queue → CryIf channel → Crypto driver-object route separately.
6. Audit the link manifest/map for sole ownership of all `Csm_*` symbols and verify the custom runtime can call the selected Crypto wrapper/provider APIs.
