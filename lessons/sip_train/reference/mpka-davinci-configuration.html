Configuration reference · inspected Vector delivery

vKeyM_MPKA on RH850 F1K / ICUS

Container-by-container plan for establishing a SecOC message-group key. Based on vKeyM_MPKA Technical Reference 4.02.00, its BSWMD, and delivered source—not a generated or target-tested ECU configuration.

Feasibility · General · Groups · Keys · PduR · Integration · Checks

0 · Resolve two implementation gates first

Gate A: the supplied ICUS crypto path is insufficient. Crypto_30_CryWrapper_Hw_KeyExchangeCalcPubVal, ...CalcSecret, and ...KeyDerive are empty implementations returning E_NOT_OK. See Crypto_30_CryWrapper_Hw.c, lines 865–940. Configuring more key containers cannot create the missing ECC/ECBD/KDF implementation.

Obtain a release-compatible crypto backend implementing the Vector ECBD workflow, both required ECDH/ECBD cases for your chosen curve, X9.63 SHA256 derivation, secure randomness, key copy, key validity, and persistence. A compatible Vector software crypto delivery is a candidate to confirm with Vector; it is not present in the inspected component set. An alternative backend needs the workflow adaptation described in TR §5.4.1. Do not replace unsupported functions with success stubs.

Check the exact security variant. The delivered F1K recommendation sets CryIcusVersion=CRY_ICUS_VERSION_ICUSE and CryNumberOfKeyslots=10 in Cry/CryGeneral. These are package recommendations, not proof of your exact silicon. Resolve your “ICUS” wording against the actual MCU part number before applying derivative settings.

ICUS AES use is a separate decision. MPKA establishes a shared secret and derives AES key material; ICUS can be used by an appropriate supported AES path after approved key loading. An AUTOSAR key copy is not automatically an ICUS/SHE protected-key import. Validate source/target key formats, permissions, actual hardware slot loading, validity, and power-cycle persistence. Do not substitute a slot ID for 16-byte key material.

Gate B: negotiation traffic is not the HV_BATT frame. secp224r1 needs 64-byte MPKA PDUs; secp256r1 needs 72-byte MPKA PDUs. Both exceed a Classical CAN frame. P224 can fit a 64-byte CAN FD payload only if the exact hardware/network supports FD; P256 cannot fit even that single frame. Your current physical transport is not established. TR §5.10.

MPKA exposes a complete-PDU IF callback, not the StartOfReception/CopyRxData/CopyTxData/TpRxIndication suite. Its generic ECUC selector lists TP, but that does not supply a transport implementation. Classical CAN requires an OEM-approved segmentation/reassembly path or a supported adapter that presents complete MPKA IF PDUs and correct TX confirmation. Do not connect it directly to CanTp just by changing CddPduRApiType. Do not invent a fragmentation format.

2 · Activate the component, not a generic stub

  1. Open the existing ECU project using the matching Vector delivery. In Project → Project Settings → Modules, add/activate the supplied vKeyM_MPKA module definition.
  2. Use the Basic Editor to edit /MICROSAR/vKeyM_MPKA/Cdd. This is the supplied CDD module definition. Do not edit the delivery's BSWMD to configure your ECU.
  3. Keep VARIANT-PRE-COMPILE, the supported MPKA variant.
  4. Activate/connect Csm, CryIf, the compatible Crypto backend, PduR, diagnostic integration, Dem/Det as required, and SchM/task scheduling. Add the selected transport modules after Gate B is resolved.

UI workflow: MICROSAR FCA SLP5 User Manual §5.2.3. MPKA variant: TR §5.1.

MPKA calls synchronous key-management APIs with key IDs. It does not reference a CsmJob for negotiation. Do not create an arbitrary MAC-generation job and use its job ID as CddKeyNegotiationGroupKeyRef. The later SecOC MAC job does use a CsmJob, whose CsmJobKeyRef must identify the committed final key (or its explicitly integrated hardware mirror). Actual driver template paths depend on the missing compatible backend. Csm BSWMD / CryIf BSWMD.

The one-byte ECU_ID crypto element is the runtime ring position, not the wider OEM ECU identity. MPKA sets it and the member count. Preserve the required driver permissions for setting, deriving, copying and clearing elements; do not indiscriminately expose secret keys to application reads. Provide the driver's secure randomness setup before key generation. TR §5.4–5.6; source lines 701–702 and 761–766.

KDF input key

  • Algorithm: ANSI X9.63 KDF with SHA256—not HKDF or PBKDF2.
  • CRYPTO_KE_KEYDERIVATION_PASSWORD: match the selected shared-value length. A conservative template allocation of 56/64 bytes also accommodates X-only if partial access is enabled and actual written length is respected.
  • CRYPTO_KE_KEYDERIVATION_SALT: one byte for this SecOC case. MPKA writes CddMsgGrpId here.
  • KDF_Input need not be persisted and may be shared according to the TR. Use a separate input key initially for easier tracing; follow backend concurrency restrictions.
Documentation discrepancy. The installed CddMsgGrpKDFInputKey description still says PASSWORD at least 56/64 bytes; TR §5.6 and §5.7 support 28/32 bytes for X-only. If validation insists on the larger allocation, enable partial access and verify actual copied length. Do not silently zero-extend X-only into X_AND_Y semantics.

Local TX reference in the group points to the TX contribution; each remote reference points to its RX contribution. The contribution itself points to EcuC. The generic RX/TX descriptions in this CDD BSWMD are confusing; the implemented API direction is decisive: RX delivers data to MPKA and TX sends its data through PduR.

PduR BSW module and routing

In PduR / PduRBswModules, identify vKeyM_MPKA as an upper-layer IF module using the supplied BSW module reference. Verify PduRUpperModule=TRUE, PduRCommunicationInterface=TRUE and PduRTxConfirmation=TRUE. Preserve unrelated module/global settings. Use the generated binding; do not forge numeric handles.

The local PduR hierarchy is PduR / PduRRoutingTables / PduRRoutingTable / PduRRoutingPath. Create:

Remote B negotiation RXLower IF transport/adapter RX PDU for BMPKA global RX PDU for B

Use PduRSrcPdu/PduRSrcPduRef and PduRDestPdu/PduRDestPduRef for the global references. For the TX IF destination use PduRDestPduDataProvision=PDUR_DIRECT and ensure PduRTransmissionConfirmation=TRUE with actual end-to-end confirmation support. DataProvision is not a required RX-route setting in the installed PduR BSWMD. For a same-core unqueued baseline, PduR data processing can be IMMEDIATE; do not suppress necessary buffering if the transport is asynchronous. No MPKA TriggerTransmit implementation is supplied.

TX: MPKA → PduR_vKeyM_MPKATransmit → transport/adapter
confirmation: transport/adapter → PduR → vKeyM_MPKA_TxConfirmation
RX: transport/adapter → PduR → vKeyM_MPKA_RxIndication

The actual source calls PduR_vKeyM_MPKATransmit, while parts of the TR spell PduR_vKeyM_MPKA_Transmit. Verify the generated header PduR_vKeyM_MPKA.h matches the source. The supplied TX callback returns Std_ReturnType; bind the actual signature from vKeyM_MPKA_Cbk.h. Do not change it to a generic guessed prototype.

Unlike a SecOC RX route: MPKA is the consumer/producer of negotiation messages; COM and SecOC do not automatically sit between MPKA and its transport. Protect negotiation transport and diagnostic authorization according to the OEM security design. Sender-ID/Proxi checks alone are not proof of cryptographic peer authentication.

7 · Diagnostics, callouts, scheduling and persistence

CddDemEvents

Bind references to real DemEventParameter instances and the OEM DTC policy. The installed mandatory references are CddKeyNegotiationUnsupportedParameter, CddKeyNegotiationSuccessful, CddKeyNegotiationTimeoutError. For this SecOC integration also configure CddKeyNegotiationFailed, CddKeyDerivationInvalidKey, and CddTooManyMessages. CddMacSecKeyNegotiationFailed and CddMacSecKeyDerivationInvalidKey apply only if MacSec is used; leave them absent for the SecOC-only configuration. Do not invent DTC numbers. Default-key-in-use tracking belongs to the callout integration.

DCM trigger

Connect the OEM diagnostic routine to the installed API:

vKeyM_MPKA_TriggerKeyNegotiation(
  delayTimeToStart, keyNegGrpId, curveID,
  OpStatus, routineInfo, ErrorCode)

The delay is 0–45 seconds. Pass the configured group ID and matching curve enum. An E_OK means triggering succeeded, not that final keys already exist. Completion is reported later by the state machine/callout and Dem. Preserve OEM routine identifiers, session/security authorization and preconditions; none can be deduced from the MPKA component alone. TR §4.1.6.

Copy/adapt _vKeyM_MPKA_Callout.c as vKeyM_MPKA_Callout.c in the integration source area. Its current Proxi functions always return E_OK. That is a template, not valid production membership logic. Inspect the template.

Startup and periodic execution

  • Initialize cleared variables using startup handling or vKeyM_MPKA_InitMemory(); call vKeyM_MPKA_Init(NULL_PTR) per the supplied API contract.
  • Ensure crypto/randomness, key provisioning/restoration, Dem and transport are ready before triggering negotiation, even though MPKA Init itself does not call adjacent services.
  • Map vKeyM_MPKA_MainFunction and vKeyM_MPKA_MainFunctionCrypto to cyclic task context with periods exactly matching CddGeneral. Account for synchronous ECC execution time and preemption.
  • Map VKEYM_MPKA_EXCLUSIVE_AREA_0 through SchM to approved locking. Do not use empty locks in a concurrent production stack.
  • Implement backend/NvM persistence for the required exchange, temporary, and final key objects. Persisting flags alone do not prove completed nonvolatile writes.
  • Provision the OEM-approved initial/default key state separately; MPKA does not initialize those values for you. After reset, an interrupted negotiation must be retriggered, not assumed resumed.

Sources: TR §3.2–3.6, §3.11.

Additional source-level integration checks

  • Member-ID width discrepancy: the ECUC member-ID range extends to 65535 and DEV is preconfigured as 999, but MessageHandling.c line 383 transmits only localMemberId & 0x7F; lines 885–886 parse only seven bits. Do not assume that arbitrary IDs in the ECUC range, including DEV=999, round-trip on the wire. Obtain the approved OEM/Vector mapping or correction before enabling those IDs; do not invent a modulo mapping.
  • TX buffer lifetime: MessageHandling.c lines 692–740 uses a stack-local message buffer. An asynchronous transport/adapter must copy the full PDU before the transmit call returns. Confirm the complete MPKA message, not each fragment. RX must provide the exact complete 64/72-byte length and the correct remote-member handle.
  • KDF driver ownership: CryIf.c lines 1396–1416 dispatches KeyDerive to the source key's driver with both driver key references. Keep KDF_Input and MAC_Temporary in a compatible same-driver configuration unless an explicit supported bridge exists. CryIf does not automatically derive into a key owned by another driver.
  • Plaintext load is RAM_KEY: Cry_30_Rh850Icus_KeyExtract.c lines 515–558 loads a plaintext key into the RAM key slot. Do not interpret that as programming an arbitrary persistent protected slot. The latter needs the approved SHE update/provisioning flow.

8 · Generate, inspect, test

  1. Run DaVinci validation, resolve reference/size/variant issues, and generate the matching module set. Inspect vKeyM_MPKA_Cfg.c/.h, vKeyM_MPKA_MemMap.h, SchM_vKeyM_MPKA.h, PduR bindings and Csm/CryIf/Crypto key mappings. Include static sources and adapted callouts in the build; the local make rule explicitly adds vKeyM_MPKA_Cfg.c.
  2. Check mapping: local/remote OEM IDs, group and message IDs, curve, runtime-position bytes, independent exchange keys, temporary/final key separation, shared/PASSWORD lengths, and 64/72-byte PDU size.
  3. Verify each required key-management service against the actual backend before a network test. A header declaration is not evidence that the implementation works.
  4. Bench-test two members and then three; confirm ECDH/ECBD selection from present membership.
  5. Trace public/intermediate exchange and TX confirmations. Never log production private/shared/final key bytes.
  6. Confirm derivation goes into the temporary key; final-key commit happens after group confirmation; prove consumer usability with an approved known-answer MAC test using disposable bench keys.
  7. Inject missing peer, wrong Proxi membership, unsupported curve, bad PDU length, crypto error/busy, missing TX confirmation and timeout. Verify error status and no false completion.
  8. Power-cycle and verify approved persisted final keys and consumer recovery. Test interrupted negotiation separately; the module has no recovery-point restart support.
What was verified here: supplied BSWMD paths and source behavior were inspected; the teaching artifacts have a separate local check report.
