HV_BATT Profile 2: PduR and ECUC map

Wire contract: secured CAN PDU = 8 bytes; Authentic PDU = 5 bytes; MAC = 3 bytes; freshness = 0 bytes.

Physical and logical layout

CAN byte 0..2  named payload signals
CAN byte 3..4  reserved/padding, fixed 0x00, authenticated
CAN byte 5..7  MAC_HV_BATT, 24-bit truncated CMAC

CMAC input = SecOCDataId (2 bytes) || AuthenticPdu (5 bytes)

If your specification numbers bytes from 1, the same map is bytes 1..3, 4..5, and 6..8. Do not leave a byte unexplained.

PduR: exactly two RX IF paths

PathPduRSrcPduRefPduRDestPduRefLength
ACanIf global secured PDUSecOC secured-PDU endpoint8 → 8
BSecOC authentic-layer PDUCOM/upper authentic PDU5 → 5

For both paths, use communication-interface routing. Use direct data provision for this fixed-length receive forwarding. Queueing, TP threshold, TriggerTransmit, gateway routing, and split processing are not part of this initial design. Set processing to immediate initially; choose deferred only if the project deliberately schedules it and validates the queue/main-function behavior.

Security boundary: Path A must not route directly to COM. COM must receive only Path B after successful SecOC verification.

Generated-code proof

  1. CanIf callback enters PduR and ultimately calls SecOC_RxIndication.
  2. SecOC calls Csm_MacVerify with Data ID plus the 5-byte Authentic PDU and the received 3-byte MAC.
  3. After success, SecOC calls PduR_SecOCRxIndication with length 5.
  4. Path B calls Com_RxIndication for the Authentic PDU.

Do not edit calculated PduR fields

Let validation/generation calculate PduRRoutingPathCommunicationType, destination handle, direction, routing type, and related IDs. Change source/destination references, regenerate, then inspect the generated callback chain.
