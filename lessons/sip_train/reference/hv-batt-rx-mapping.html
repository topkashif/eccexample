Reference card · HV_BATT

Final I-PDU and padding contract

The requirement confirms that the grey bytes are zero padding, and that the 7-byte CMAC input is Data ID plus five signal bytes.

Physical CAN-HS message

BytesContentCMAC treatment
0HV_BATTERY_SOCE_DISPIncluded

5–7MAC_HV_BATT, 24 bitsCompared with calculated MAC

7-byte CMAC input

Data ID       = MGRP.ID || M.ID = 02 02
Authentic PDU = CAN bytes 0..4
               = payload bytes || 00 00 padding
Freshness     = empty
CMAC input    = 02 02 || CAN[0] || CAN[1] || CAN[2] || 00 || 00
Received MAC  = CAN[5] || CAN[6] || CAN[7]

The requirement calls this combined 7-byte sequence the I-PDU input to CMAC: 1 byte MGRP.ID, 1 byte M.ID, and 5 bytes of signals, including zero padding where necessary.

SecOC configuration consequence

The previous secured-area length of 3 bytes was incorrect. The complete five-byte Authentic PDU, including the two zero padding bytes, is authenticated.

  • Preferred: do not create SecOCRxPduSecuredArea; Vector then uses the complete Authentic PDU.
  • Explicit alternative: configure SecOCRxPduSecuredArea with SecOCSecuredRxPduOffset = 0 and SecOCSecuredRxPduLength = 5.

RX-only baseline

  • 8-byte received secured PDU.
  • SecOCAuthInfoTruncLength = 24 bits.
  • SecOCFreshnessValueLength = 0.
  • SecOCFreshnessValueTruncLength = 0.
  • Generated Data ID bytes: 02 02.
  • Secured RX verification enabled.
  • Deferred processing initially.
  • No TX processing for this ECU.

Verification consequence

Bytes 3–4 are not ignored anymore. They are required to be zero and are included in the CMAC input. Changing either byte to a nonzero value changes the CMAC and must cause verification failure unless a new MAC is generated over the changed value.

If the receiver must reject nonzero padding even when a matching MAC exists, add a separate reserved-byte validity check as well.
