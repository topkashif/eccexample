Lesson 09 · CANoe integration

Put the SecOC frame in CANoe without confusing DBC with security configuration

Today’s win: make CANoe display the correct 8-byte bus frame, then give Security Manager the separate SecOC meaning needed to generate and validate the 24-bit CMAC.

Version note: CANoe 12 menu names and licensed Security Manager features must be confirmed in the installed Help. The workflow below is the stable object model; exact labels may vary by CANoe 12 service pack and Security Manager/OEM add-on.

1. What the DBC must describe

Your DBC message must be the physical secured CAN frame, not only the five-byte Authentic PDU:

CAN ID: project HV_BATT ID
DLC = 8, Classical CAN

byte 0     HV_BATTERY_SOCE_DISP
byte 1–2   HVBatt_NetEnrgy_Consumd_OBM_Trip
byte 3–4   reserved/zero padding
byte 5–7   MAC_HV_BATT, 24 bits
DBC elementPurpose
Message, CAN ID, DLCDefines the physical frame CANoe sends/receives.
Payload signalsDecodes application data for display and stimulation.
Reserved bytes 3–4Keep visible/controlled as zero; they remain authenticated data.
MAC_HV_BATTDisplays the received three-byte authenticator; it does not by itself activate SecOC.
Prediction: If the DBC message has DLC 5, can CANoe reproduce the ECU’s physical secured PDU? No. The configured message must carry all 8 bytes.

2. Add and validate the ordinary CAN database first

  1. Add the DBC to the CANoe network configuration.
  2. Map the network to the correct CAN channel/interface.
  3. Confirm HV_BATT appears with DLC 8.
  4. Observe bytes 0–7 in Trace/Details.
  5. Confirm the two reserved bytes are not accidentally omitted, shifted, or treated as MAC bytes.

Do this before enabling Security Manager. Otherwise a DBC placement problem and a CMAC problem become indistinguishable.

3. Configure the SecOC security object

Open the CANoe Security Configuration/Security Manager workflow provided by your CANoe 12 installation. Add a SecOC protected-PDU/security object and associate it with the CANoe database message and simulation controller/port that will send the valid frame.

Enter the active project contract:

SecOC profile:             Profile 2 / 24Bit-CMAC-No-FV
Algorithm:                AES-128 CMAC
Data ID:                  0x0202
Secured frame length:     8 bytes
Authentic area:           offset 0, length 5
Authenticator:            bytes 5–7, 24 bits
Full/transmitted FV:      0 bits
Padding bytes:            bytes 3–4 = 00 00

If CANoe instead asks for separate secured/authentic PDU mappings, map:

secured PDU   = HV_BATT CAN frame, 8 bytes
authentic PDU = bytes 0..4, 5 bytes
authenticator = bytes 5..7, 3 bytes

4. Configure the test key

Use Security Manager’s key/profile management to add a test-only AES-128 key and associate it with Data ID 0x0202 or the SecOC PDU object, according to the CANoe 12 UI. Never put a production key in the DBC, CAPL, repository, or chat.

For documentation use:

test AES-128 key = [REDACTED]
Data ID          = 0x0202

5. Expected valid frame

For payload bytes CAN[0..2], CANoe should generate:

CMAC input = 02 02 || CAN[0] || CAN[1] || CAN[2] || 00 || 00
CAN[5..7]  = first 3 CMAC bytes, under the configured MSB truncation rule

Use Trace to verify both the bytes on the bus and the values decoded by the DBC. The ECU should then follow:

CanIf → PduR Path A → SecOC → CSM/Crypto
      → verified Authentic PDU → PduR Path B → COM/application

6. Minimal test sequence

TestCANoe actionExpected ECU result

Payload corruptionChange byte 0, 1, or 2 without recalculating MAC.Verification fails; no normal COM indication.
Padding corruptionChange byte 3 or 4 from 00 without recalculating MAC.Verification fails because padding is authenticated.
MAC corruptionFlip a bit in byte 5, 6, or 7.Verification fails.
ReplayReplay a previously valid frame.May be accepted: no-freshness Profile 2 does not provide replay protection.
Wrong key/Data IDUse a wrong test key or Data ID.Verification fails.

7. Diagnose by evidence

  • DLC/MAC position wrong in Trace: DBC or secured-PDU mapping problem.
  • MAC never changes with payload: Security Manager mapping/key/profile is inactive.
  • CANoe frame looks valid but ECU rejects it: compare Data ID bytes, key, Authentic-PDU bytes, padding, truncation, and byte order.
  • ECU never reaches SecOC: inspect PduR Path A; it must terminate at the SecOC secured PDU, not COM.
  • SecOC verifies but application sees nothing: inspect PduR Path B and the five-byte Authentic-PDU destination.
  • Bad MAC reaches application: check development mode, forced-pass/ignore-verification settings, and whether Path A bypasses SecOC.
