Lesson 11 · IPC integration · vKeyM_MPKA + SecOC + RH850/ICUS

Make the final key do the job

Your tangible win: configure the IPC/EVCU two-member MPKA relationship and trace exactly how the committed message-group key reaches SecOC MAC verification.

First, the boundary. The supplied vKeyM_MPKA orchestration is present, but the inspected CryptoWrapper key-exchange and KDF leaf functions return E_NOT_OK. This lesson teaches the correct integration contract; it does not claim the current ICUS-only delivery can complete MPKA on target.

In the installed BSWMD, use CddKeyNegotiationGroup, one remote-member entry for EVCU, and one CddMessageGroup. The local IPC member is implicit. The delivered source packs the member ID into seven wire bits; IDs 3 and 4 are compatible with that observed format.

2 · Predict before looking

Which key should the SecOC MAC job reference: the exchange key, the temporary key, or the committed message-group key?

3 · The four-key graph

CddKeyNegotiationGroupKeyRef → KEX_Group_2
CddMsgGrpKDFInputKey         → KDF_Input_2
CddMsgGrpTmpKey              → MAC_Temporary_2
CddMsgGrpKey                 → MAC_Final_2

ECDH shared value
  → KDF_Input_2.PASSWORD
  → KDF_Input_2.SALT = {0x02}
  → X9.63-SHA256 KDF
  → MAC_Temporary_2 (16 bytes)
  → group confirmation
  → MAC_Final_2
  → SecOC CsmJobKeyRef

The one-byte salt is the MPKA message-group ID. It is not automatically the full two-byte SecOC Data ID, and it must not be duplicated in the SecOC CMAC input.

4 · What the generated SecOC call means

Csm_MacVerify(
  authenticationLayerId,  // generated CSM job ID
  SINGLECALL,
  dataToAuthenticate,
  dataLength,
  receivedMac,
  24,                     // bits
  verifyResultPtr);

The job ID is resolved by generated CSM configuration. Its CsmJobKeyRef must point to MAC_Final_2. It must not be reinterpreted as an ICUS key ID or replaced with a boot-key constant.

5 · If reusing SecurityLib

The local secoc_securitylib_csm_wrapper.c is a narrow adapter. Keep generated Csm.c and route only the generated SecOC job IDs to the adapter through an approved project dispatch point.

startup:
  SecOcSecurityLib_ConfigureMessageGroup(generated handles)

successful vKeyM_MPKA_KeyNegotiationFinalized(2, SUCCESSFUL):
  Csm_KeyElementGet(MAC_Final_2, CRYPTO_KE_MAC_KEY)
  require 16 bytes
  SecLib_KeyRAMUpdate(key, 16)
  activate

SecOC verification:
  job ID matches configured RX job
  SecLib_MACVerify(KEY_RAM, data, 7, mac, 3)
  mismatch → E_OK + CSM_E_VER_NOT_OK
  service failure → E_NOT_OK

Do not add another global Csm_MacVerify(). The generated CSM already fills a job object and dispatches it through Csm_ProcessJob; duplicate definitions can recurse, collide at link time, or bypass the configured primitive/key chain.

6 · Verify on the target

  1. Inspect generated symbolic handles: MAC_Final_2, RX verify job, and optional TX generation job.
  2. Confirm the RX job points to MAC_Final_2.
  3. Breakpoint at SecOC_VerifyProcessing_MACUsingCSM43(); inspect Data ID, authentic data, data length, MAC pointer, and 24-bit length.
  4. On successful finalization, prove the adapter activates only after final-key read/length/load succeeds.
  5. Send a valid frame, then mutate payload, authenticated padding, MAC, Data ID, and key activation state.
  6. Only a valid frame may reach PduR_SecOCRxIndication. Do not log secret key bytes.
