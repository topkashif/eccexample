Lesson 10 · RX observability

Prove SecOC verification without looking for an ACK

Your ECU is an RX-only node. The correct evidence is the ECU receive pipeline and the verified Authentic-PDU handoff—not an application acknowledgement on CAN.

For this frame, the received MAC is in physical bytes CAN[5..7]; the authenticated data is bytes CAN[0..4], including the two zero padding bytes.

Key distinction: a CAN ACK only means a CAN controller recognized the frame at the bus level. It does not mean that SecOC accepted the MAC, that CSM verified CMAC, or that COM received the signal.

2. First breakpoint: SecOC entry

Set a breakpoint or tracepoint in:

SecOC_RxIndication()
components/SecOC/Implementation/SecOC_RxIf.c:218

For the HV_BATT frame, inspect:

id
info->SduLength       == 8
info->SduDataPtr[0..7]

The local implementation rejects an uninitialized module, invalid PDU ID, null data pointer, and too-short/mismatched configured length in the checks around lines 224–264.

If this breakpoint is never hit: stop debugging SecOC. Check CAN channel/filtering, CanIf RX PDU mapping, PduR Path A, and the generated secured-PDU handle first. If it is hit but takes the uninitialized branch, seeing SecOC_Init() return is not enough: that API is void. Prove its success path reached SecOC_SetInitialized(TRUE), then check whether SecOC_InitMemory() or SecOC_DeInit() cleared it later. See Lesson 11.

3. Confirm the secured frame entered the RX state machine

Next inspect:

SecOC_RxIf_RxIndication()
components/SecOC/Implementation/SecOC_RxIf.c:310

For a normal non-split PDU, the local source calls:

SecOC_RxIf_NormalPduIndication()    // copies the secured frame
SecOC_Verify_CopyAuthenticatorToCache() // caches bytes 5..7
SecOC_RxIf_SetReadyToVerifyStates() // resets attempts and sets state

The relevant normal-PDU branch is around lines 327–333. Verify that the generated configuration identifies this as a normal IF PDU, not a split or TP PDU.

4. Deferred versus immediate processing

Your initial configuration uses deferred processing. The source selects immediate processing only when the generated PDU configuration says so:

SecOC_RxIf_SetReadyToVerifyStates()
components/SecOC/Implementation/SecOC_RxIf.c:130–143

For deferred processing, verify that the generated scheduler calls the configured RX main function. The Vector implementation enters:

SecOC_MainFunctionRxInternal()
  → SecOC_RxProcessing_HandlePdus()
  → SecOC_Verify_MAC()

These are in SecOC_RxProcessing.c around lines 294, 314, and 339. AUTOSAR requires SecOC_MainFunctionRx to process pending RX verification and, after successful verification, pass the Authentic PDU upward.

24 bits
Important: CSM’s macLength parameter is in bits. The local CSM header documents this explicitly, and SecOC passes the generated truncated-authentication length directly.

6. Synchronous and asynchronous crypto paths

If CSM/Cry is synchronous, the CSM call may return the verification result immediately and SecOC continues in the same processing path.

If it is asynchronous, the state changes to a callback-wait state and the crypto completion must return through:

SecOC_RxCsmCallback(
  PduIdType rxHandleId,
  Csm_ResultType result)

components/SecOC/Implementation/SecOC_RxProcessing.c:236

The callback checks the waiting state, stops timeout supervision, and may call SecOC_Verify_MAC() immediately if configured. Otherwise, the next RX main-function invocation processes the result.

For the local RH850 CRY implementation, the CMAC verify main function calls:

Csm_MacVerifyCallbackNotification(retVal)
Csm_MacVerifyServiceFinishNotification()

in the asynchronous state-machine path. If the CSM callback never reaches SecOC, inspect the generated CSM job callback ID, CSM/Cry processing mode, Cry main-function scheduling, and SecOC_RxCsmCallback linkage.

7. Success evidence: the five-byte Authentic PDU is forwarded

On a successful CSM result, the local source calls:

SecOC_VerifyProcessing_ProcessSuccessfulVerificationResult()
components/SecOC/Implementation/SecOC_VerifyProcessing.c:571

It prepares a PduInfoType from the configured Authentic-PDU buffer and length, then calls:

SecOC_RxProcessing_ForwardPduToUpperLayer()
components/SecOC/Implementation/SecOC_RxProcessing.c:364

For an IF PDU, the decisive handoff is:

PduR_SecOCRxIndication(
  authenticExternalId,
  pduInfoPtr);

The local implementation calls it around SecOC_RxProcessing.c:369–371. For HV_BATT, inspect that:

pduInfoPtr->SduLength == 5
pduInfoPtr->SduDataPtr[0..4] == Authentic PDU

At the generated Path B destination, often Com_RxIndication(), confirm that COM receives the five-byte verified Authentic PDU—not the eight-byte secured frame and not the three-byte MAC.

8. Failure evidence

For a bad payload, bad padding byte, or bad MAC, the expected path is:

Csm_MacVerify() called
verification result != OK
SecOC_VerifyProcessing_ProcessUnsuccessfulVerificationResult()
no normal PduR_SecOCRxIndication() to COM

The failure handler is in SecOC_VerifyProcessing.c:229. It increments verification attempts, optionally propagates a failure status, retries if configured, and eventually sets the RX PDU to an aborted state.

For this first test, keep these bypass mechanisms disabled:

SecOCEnableDevelopmentMode       = FALSE
SecOCIgnoreVerificationResult    = FALSE
verification override             = CANCEL
status propagation                = NONE is acceptable

Status propagation being NONE does not disable verification. It only means no application status callback is expected.

9. Minimal target instrumentation

If debugger tracing is inconvenient, add temporary non-secret counters:

rx_enter_count
rx_buffered_count
mac_verify_request_count
csm_callback_ok_count
csm_callback_fail_count
secoc_verify_success_count
secoc_verify_failure_count
authentic_forward_count

Also record only metadata:

last secured length = 8
last authentic length = 5
last Data ID = 0x0202
last MAC length = 24 bits
last generated CSM job ID = [project value]

Never log the AES key.
