Lesson 08 · one integration win

Do not add symbols one by one: restore the SecOC generated boundary

The compiler errors are telling you that the vendor implementation was copied without the generated configuration and integration layer. Your next win is to separate those layers before writing any compatibility code.

Correction to the earlier shorthand: Rte_SecOC_Type.h is specified by AUTOSAR for RTE-visible SecOC types, but the local Vector C source does not include it directly. Do not assume that every missing type should be solved by manually creating that file; first locate the generated SecOC configuration/header that your package expects.

2. Why SECOC_FRESHNESSFAILURE appears in a no-freshness project

The Vector source is one configurable implementation. Its generic RX state machine contains the freshness-error path and calls:

SecOC_Verify_PropagateVerificationStatus(
  rxPduId,
  SECOC_FRESHNESSFAILURE);

AUTOSAR CP R23-11 defines the verification result values in the RTE-visible SecOC type family:

SECOC_VERIFICATIONSUCCESS              0x00u
SECOC_VERIFICATIONFAILURE              0x01u
SECOC_FRESHNESSFAILURE                 0x02u
SECOC_AUTHENTICATIONBUILDFAILURE       0x03u
SECOC_NO_VERIFICATION                  0x04u
SECOC_VERIFICATIONFAILURE_OVERWRITTEN  0x05u

Your configured HV_BATT PDU still has zero freshness length. That means the active cryptographic input remains:

02 02 || CAN[0] || CAN[1] || CAN[2] || 00 || 00

It does not mean the generic source can be edited to remove the freshness-result enum. The generated configuration must select the active path.

3. Why the SchM errors are different

SchM_Enter_SecOC_... is not a data type. It is a synchronization contract generated by the Schedule Manager integration. The local source uses four names:

SchM_Enter_SecOC_SECOC_EXCLUSIVE_AREA_RXSTATE()
SchM_Exit_SecOC_SECOC_EXCLUSIVE_AREA_RXSTATE()
SchM_Enter_SecOC_SECOC_EXCLUSIVE_AREA_TXSTATE()
SchM_Exit_SecOC_SECOC_EXCLUSIVE_AREA_TXSTATE()

RXSTATE is used around receive state and the RX CSM callback. TXSTATE is used by generic TX code even though your application is RX-only. The safe choices are:

  • bring the project-generated SchM_SecOC.h from the same OS/SchM generation;
  • if the project explicitly owns SchM integration, map both enter/exit pairs to the approved interrupt/resource-lock mechanism;
  • for a strictly single-threaded compile experiment only, use empty macros temporarily and mark the result non-production.

Do not declare these macros as ordinary functions with guessed return values. Do not remove TX source just because this ECU does not transmit; doing so can create a different, unsupported build variant.

4. The exact status callback distinction

There are three different things that are easy to confuse:

NameMeaningShape in the local source
SecOC_VerificationResultTypeOne result valueUsed as the argument to propagation functions
SecOC_VerificationStatusTypeBundle of result, freshness ID, and SecOC Data IDLocal object verificationStatusStruct
SecOCRteVerificationStatusTypeVector-generated callback-pointer typeCalled with &verificationStatusStruct

In the local SecOC_Verify.c, the generated callback is called only when its function pointer is non-null:

if(rteVerificationStatus != NULL_PTR)
{
  (void)rteVerificationStatus(&verificationStatusStruct);
}

That is why the correct fix is normally to configure status propagation to NONE and regenerate when no application status is needed—not to add a guessed callback implementation.

5. Your first HV_BATT configuration decision

For the first RX authentication experiment, if you only need to prove acceptance/rejection and forwarding to COM:

SecOCVerificationStatusPropagationMode              = NONE
SecOCClientServerVerificationStatusPropagationMode  = NONE
SecOCVerificationStatusWithSecuredPduPropagationMode = NONE
SecOCVerificationStatusCallout                     = no entries
SecOCVerificationStatusCalloutWithSecuredPdu       = no entries
SecOCQueryFreshnessValue                            = CFUNC (project default)
SecOCUseGetRxFreshness                               = FALSE
SecOCUseGetRxFreshnessAuthData                       = FALSE
SecOCEnableCustomAuthenticationAPI                  = FALSE

Then verify the generated configuration. The three status propagation modes are present in the local BSWMD and each defaults to NONE. This avoids an application RTE status port, but it does not eliminate the need for the complete generated SecOC configuration.

6. What to copy from the DaVinci output

Use the generated output directory, not the component source directory, as the source of truth. The local make rules explicitly expect:

GENERATED_SOURCE_FILES += $(GENDATA_DIR)\\SecOC_PBcfg.c \\
                          $(GENDATA_DIR)\\SecOC_Lcfg.c
include $(GENDATA_DIR)\\Make\\SecOC_rules_generated.mak

Find and integrate, as applicable:

  • generated SecOC configuration headers and sources;
  • the generated SecOC_MemMap.h convention used by your compiler;
  • SchM_SecOC.h;
  • the generated PduR-to-SecOC interface header;
  • the generated CSM callback/job configuration that names SecOC_RxCsmCallback;
  • RTE type/callback output only if an RTE service interface is enabled;
  • the matching make fragment or project file entries.
Release match: the local SecOC.h identifies MICROSAR SecOC 19.02.06. Generated headers, configuration accessors, callback typedefs, memory maps, and SchM contracts must be generated by the compatible Vector package and configuration variant.

7. A controlled compatibility layer, if RTE truly cannot be generated

A compatibility layer is acceptable only when it mirrors the generated interface and the configuration has disabled the corresponding optional feature. It belongs in a project integration directory, not in the vendor source folder.

For example, a project-owned status-free build may need a release-matched type header containing the standard semantic types and a release-matched SchM_SecOC.h. However, you must still obtain the exact generated declarations for:

  • all configuration accessors and tables;
  • the SecOC initialization configuration object;
  • the CSM callback table and authentication-layer job ID;
  • the PduR handles and callback prototypes;
  • the memory-map sections.

Do not create only enough definitions to make one translation unit compile. That can produce a linkable but functionally unconfigured SecOC.

8. Verification gate

  1. Preprocess one SecOC translation unit and confirm the generated headers resolved without fallback placeholders.
  2. Search the preprocessed/generated output for the HV_BATT PDU’s secured/authentic IDs, lengths, Data ID bytes, and CSM job ID.
  3. Confirm SecOC_RxIndication is the Path A destination and PduR_SecOCRxIndication is the verified Path B handoff.
  4. Confirm Csm_MacVerify receives the configured authentication-layer job ID and 24-bit truncated MAC length.
  5. Confirm the RX CSM callback is linked; for asynchronous CSM, confirm it returns into SecOC under the SchM RXSTATE protection.
  6. Only then investigate ordinary undefined references such as Det, IdsM, EcuM, or application callbacks.
