Lesson 05 · PduR routing diagnosis

Make PduR route the right PDU to the right module

The key routing rule is simple: the secured 8-byte PDU goes into SecOC; only the verified 5-byte Authentic PDU goes to COM.

Immediate diagnosis. If Path A currently has a PduRDestPdu referencing COM, it is not the SecOC receive path. It is a direct CanIf → COM route. For this RX-only secured message, replace that destination with the SecOC secured-PDU endpoint, then create a separate Path B whose destination is COM.

2. Path A — CanIf to SecOC

CAN controller
  → CanIf Rx PDU: HV_BATT_SecuredPdu, length 8
  → PduR source PDU
  → PduR destination PDU: HV_BATT_SecuredPdu, endpoint SecOC
  → SecOC_RxIndication()
  → SecOC extracts Authentic[5] and MAC[3]

What to configure

  1. In CanIf, configure the received global PDU with Classical CAN length 8 and upper-layer indication PDUR.
  2. In SecOC, configure SecOCRxSecuredPduLayer → SecOCRxSecuredPdu.
  3. Set SecOCRxSecuredLayerPduRef to the same global 8-byte secured PDU used by CanIf.
  4. Set SecOCSecuredRxPduVerification = TRUE.
  5. In PduR, create a communication-interface routing path with the CanIf PDU as PduRSrcPduRef.
  6. Configure its PduRDestPduRef to the secured-PDU destination associated with SecOC—not the COM PDU.
  7. Use direct IF data provision and no queue for the initial fixed-length test.
Do not route Path A to COM. COM would receive the MAC-bearing 8-byte secured frame before SecOC has authenticated it. That bypasses the security boundary and can also create a length mismatch if COM expects the 5-byte Authentic PDU.

3. Resolving the current COM destination in Path A

There are two common DaVinci situations. Identify which one you have.

Case 1 — The route is genuinely CanIf → COM

In the PduR routing-path view, the source is the CanIf Rx PDU and the destination module is COM. This is a normal unprotected communication route.

Resolution:

  1. Remove or disable that direct route for the secured HV_BATT PDU.
  2. Keep the global 8-byte secured PDU for CanIf and SecOC.
  3. Create the SecOC RX secured-PDU configuration and reference that same global PDU.
  4. Create Path A with source CanIf and destination SecOC.
  5. Create Path B separately with source SecOC and destination COM.

Case 2 — The GUI shows COM because the global PDU is COM-owned

Some Vector views show the owner or communication description of the global PDU rather than the actual PduR endpoint. In that case, the displayed COM association alone is not enough to diagnose the route.

Resolution: inspect the actual routing endpoint and generated code. The decisive test is whether the generated CanIf receive route calls SecOC_RxIndication or Com_RxIndication. For a correct Path A it must call SecOC. If it calls COM, configure the route's destination endpoint as SecOC or let the SecOC/PduR integration wizard regenerate the route from the SecOC references.

Do not edit calculated parameters

In the local Vector PduR BSWMD, parameters such as PduRDestPduHandleId, PduRDestPduDirection, PduRDestPduRoutingType, and PduRRoutingPathCommunicationType are calculated by validation/generation. Change the source/destination PDU references and module endpoint; then regenerate. Do not hand-edit generated IDs or calculated direction/type values.

4. Path B — SecOC to COM, in detail

SecOC verification succeeds
  → SecOC builds PduInfoType for Authentic PDU
      SduDataPtr = Authentic[0..4]
      SduLength  = 5
  → PduR_SecOCRxIndication(authentic external handle, &PduInfo)
  → PduR source PDU lookup
  → PduR destination PDU
  → Com_RxIndication(COM PDU handle, &PduInfo)
  → COM signal unpacking / upper consumer

Path B configuration

  1. In SecOC, configure SecOCRxAuthenticPduLayer.
  2. Set SecOCRxAuthenticLayerPduRef to a global 5-byte Authentic PDU.
  3. Ensure the SecOC PDU type is an IF PDU: SecOCPduType = SECOC_IFPDU.
  4. Configure the authentic PDU ID generated/assigned by SecOC. Do not choose a numeric handle by guesswork.
  5. In PduR, use the SecOC authentic PDU as PduRSrcPduRef.
  6. Use the COM-facing Authentic PDU as PduRDestPduRef.
  7. Configure the destination's data provision as direct. The PduR Technical Reference states that direct provision copies the PDU while calling the destination transmit/indication function; TriggerTransmit is not needed for this receive forwarding path.
  8. Do not put the 3-byte MAC in the COM PDU. COM receives only the 5-byte Authentic PDU.

What COM should see

COM's receiving I-PDU must describe the authenticated data, not the physical secured frame. Its length must match the Authentic PDU, normally 5 bytes for this contract. The two padding bytes remain part of that PDU; COM may model them as reserved/unused bits or a padding field, but SecOC must have authenticated them before COM sees the data.

COM should not be responsible for:

  • extracting the MAC;
  • checking the 24-bit authenticator;
  • constructing the Data ID;
  • deciding whether the frame is authentic.

The local Vector source confirms this separation: the RX processing code calls PduR_SecOCRxIndication only when the PDU is an IF PDU after successful verification, and the verification-success function passes the Authentic PDU buffer and length upward. The AUTOSAR PduR model then maps that SecOC source PDU to the COM destination PDU.

Practical next action. In DaVinci, inspect Path A and write down: source module, source global PDU, destination module, destination global PDU, and generated destination handle. If the destination module is COM and the generated callback is Com_RxIndication, reconfigure it as described above. If the GUI still displays COM but generated code calls SecOC, the display is showing PDU ownership rather than the effective endpoint.
