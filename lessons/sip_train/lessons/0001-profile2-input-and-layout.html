Lesson 01 · 5–8 minutes

Configure the security contract before opening DaVinci

Your first tangible win: turn “Profile 2, 24-bit CMAC, no FV” into an unambiguous byte-level contract that TX, RX, CSM, and the test bench can all share.

Mission link. This is the smallest useful unit for your RH850 F1K1/ICUSE target: if the input and output bytes are not fixed first, hardware-driver debugging later becomes misleading.

1. The profile in one equation

CMAC = AES-CMAC-128(K, DataId || AuthenticPdu)
Authenticator = MSB_24(CMAC)
SecuredPdu = AuthenticPdu || Authenticator

AUTOSAR describes Profile 2 as AES-128 CMAC with the 24 most-significant MAC bits and no freshness value. For the explicit no-FV configuration, set the complete FV length and transmitted FV length to zero, while the authentication-information truncation remains 24 bits. See AUTOSAR Protocol R24-11 §5.3.3.

2. Treat the Data ID as authenticated input

In the Vector implementation, the CSM43 authenticator inserts the configured two-byte Data ID into the data-to-authenticate buffer before calling Csm_MacGenerate. The local source shows this in SecOC_CSM43Authenticator.c: the Data ID is written first, then Csm_MacGenerate receives the assembled input.

Implication: the receiver must use the same numeric Data ID and the same two-byte serialization. A correct AES key with a wrong Data ID still produces a failed verification.

These are defined for both SecOCRxPduProcessing and SecOCTxPduProcessing in the local BSWMD: RX around lines 2556–2805; TX around lines 4523–4682.

Important discrepancy to recognize. The current AUTOSAR R24-11 protocol PDF contains an explicit no-FV table with 0/0/24, but also shows an earlier-looking table row with “Not Specified/8 bits/24 bits.” For your stated requirement, the no-FV row is the applicable one. We will verify the generated ECUC and wire layout rather than trusting a profile name alone.

4. Practice: predict the wire length

Suppose the Authentic PDU is 5 bytes. Without headers, split PDUs, or CAN-FD padding, what should the Secured PDU contain?

Write your answer before revealing it.

8 bytes: 5 authentic bytes + 3 authenticator bytes. There is no FV field.

5. Your bring-up checklist

  1. Choose one ordinary IF PDU first; avoid split PDU and transport protocol until the basic path works.
  2. Allocate one unique 16-bit Data ID and record it in the test specification.
  3. Configure TX and RX with identical Data ID, CMAC job, key, and truncation values.
  4. Capture one TX frame and independently recompute AES-CMAC over DataId || AuthenticPdu.
  5. Confirm the three transmitted authenticator bytes are the CMAC's most-significant 24 bits.

Primary reading

Read only §5.3.3 of the AUTOSAR SecOC Protocol, then scan the local cheat sheet.
