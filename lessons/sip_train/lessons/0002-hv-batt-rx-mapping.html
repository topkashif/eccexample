Lesson 02 · revised worked example

Configure zero padding as authenticated I-PDU data

The requirement resolves the earlier ambiguity: the physical HV_BATT message contains five signal bytes before the MAC. Two of those bytes are zero padding, and all five are authenticated.

Revision. The previous “exclude bytes 3–4” conclusion was incorrect. The requirement explicitly says the grey bits are set to zero in both the CAN frame and the I-PDU, and the 7-byte I-PDU is the CMAC input.

1. Physical layout

CAN byte 0     HV_BATTERY_SOCE_DISP
CAN byte 1..2  HVBatt_NetEnrgy_Consumd_OBM_Trip
CAN byte 3..4  padding = 0x00 0x00
CAN byte 5..7  MAC_HV_BATT, 24 bits

The received secured PDU is 8 bytes: a 5-byte Authentic PDU followed by a 3-byte truncated authenticator.

2. Seven-byte CMAC input

The requirement defines the I-PDU used as CMAC input as:

byte 0  MGRP.ID = 0x02
byte 1  M.ID    = 0x02
byte 2  HV_BATTERY_SOCE_DISP
byte 3  EnergyByte0
byte 4  EnergyByte1
byte 5  0x00 padding
byte 6  0x00 padding

Equivalently, using the SecOC model:

Data ID       = 02 02
Authentic PDU = CAN bytes 0..4
CMAC input    = 02 02 || CAN[0..4]
               = 02 02 || payload || 00 00
Received MAC  = CAN[5..7]

This is AES-128 CMAC with no freshness value, and the received MAC is compared with the 24 most-significant CMAC bits.

3. Correct Secured Area setting

Because bytes 3–4 are padding but are part of the five signal bytes, the authenticated area is five bytes, not three.

OptionConfiguration
PreferredDo not create SecOCRxPduSecuredArea; the complete Authentic PDU is used.
ExplicitSecOCSecuredRxPduOffset = 0, SecOCSecuredRxPduLength = 5

The local BSWMD says that without a secured-area container, the complete Authentic PDU is used. If an explicit container is used, its length must be 5 bytes so that the two zero padding bytes remain in the CMAC input.

5. Padding verification

  1. Valid frame with bytes 3–4 equal to zero: MAC verification passes.
  2. Change byte 0, 1, or 2 without recalculating MAC: verification fails.
  3. Change byte 3 or 4 to nonzero without recalculating MAC: verification fails because padding is authenticated.
  4. Change any MAC bit in bytes 5–7: verification fails.

If the sender generated a new MAC over nonzero bytes 3–4, the CMAC could mathematically match, so add a separate zero-padding check if the requirement demands that reserved bytes always be zero independently of authentication.

6. No-FV nuance

Profile 2 means no freshness bytes are transmitted and no freshness bytes contribute to CMAC. The Vector standard RX route may still select a zero-length freshness API; inspect the generated RX function table. This does not alter the 7-byte CMAC input above.
