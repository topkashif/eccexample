Lesson 04 · ECUC configuration

Configure one RX-only SecOC Profile 2 PDU, container by container

This is the practical DaVinci configuration map for the RH850 F1K1 ICUSE receiver. It separates AUTOSAR container semantics from Vector-specific names and keeps the HV_BATT byte contract visible at every step.

Mission link. Configure and later prove this exact contract: Classical CAN, an 8-byte secured PDU, a 5-byte Authentic PDU, a 3-byte authenticator, AES-128 CMAC, 24-bit MSB truncation, and no freshness value.

0. Freeze the contract before opening DaVinci

ObjectRequired valueWhere it belongs
Physical secured CAN PDU8 bytes: payload bytes 0–4, MAC bytes 5–7CAN matrix / CanIf / SecOC secured PDU
Authentic PDU5 bytes: CAN[0..4], including padding 00 00SecOC RX Authentic PDU layer
Data Identifier0x0202, encoded for CMAC as 02 02SecOC RX PDU processing
DataToAuthenticator02 02 || CAN[0] || CAN[1] || CAN[2] || 00 || 00, 7 bytesSecOC internal cryptographic buffer
AuthenticatorCAN[5..7], 24 bitsSecOC cryptographic extraction / CSM verify input
Length trap. Do not configure a 7-byte SecOC Authentic PDU or a 3-byte secured area. The routed Authentic PDU is 5 bytes. The 7-byte quantity is the internal DataToAuthenticator buffer after SecOC prepends the 2-byte Data ID.

1. Global PDU objects: the shared references

Before configuring module-specific containers, make sure the project contains global PDU objects that every module can reference. The AUTOSAR specifications describe these as references to a global PDU; Vector's project model may present them through the communication description and generated PDU handles.

Required global PDU concepts

  • HV_BATT_SecuredPdu: the physical 8-byte CAN PDU received by SecOC.
  • HV_BATT_AuthenticPdu: the 5-byte data portion delivered upward after successful verification.
  • Optional cryptographic PDU: not needed for this single-frame layout. Use the SecOC single SecOCRxSecuredPdu choice, not SecOCRxSecuredPduCollection.

The names above are instructional names, not mandatory Vector short names. Use your project's actual global PDU names.

2. CanIf: accept exactly the Classical CAN frame

In the AUTOSAR R23-11 CAN Interface specification, the receive configuration is under CanIf/CanIfInitCfg/CanIfRxPduCfg. The local Vector BSWMD uses the same concepts.

For the fixed PDU, do not configure a CAN-ID range, dynamic Rx ID, CAN XL container, or CAN-FD type. Confirm the 16-bit signal's byte serialization against the sender's DBC; SecOC authenticates the resulting bytes, not the signal's engineering value.

Primary source: AUTOSAR CAN Interface R23-11, section 10.1.7 CanIfRxPduCfg.

3. PduR: create two ordinary IF routing paths

AUTOSAR PduR routing is static. A routing path has one source and one or more destinations. PduR forwards the PduInfoType; it does not inspect or modify the CMAC payload.

Path A — secured PDU into SecOC

  1. Create a PduRRoutingPath for communication-interface reception.
  2. Create PduRSrcPdu referencing the CanIf receive PDU.
  3. Create PduRDestPdu referencing the SecOC secured-layer PDU.
  4. Use the generated source and destination handle IDs; do not hand-edit calculated IDs.
CanIf Rx PDU (8 bytes)
  → PduR source
  → SecOC secured Rx PDU

Path B — verified Authentic PDU upward

  1. Create a second IF routing path.
  2. Use the SecOC authentic-layer PDU as the source.
  3. Use the COM or upper consumer PDU as the destination.
  4. Configure the destination for direct IF data provision initially.
SecOC Authentic PDU (5 bytes)
  → PduR source
  → COM / upper consumer

For this single-frame, non-TP path, omit TP thresholds, gateway buffers, TriggerTransmit provision, fan-in, and routing-path queues unless the rest of the project specifically requires them. The AUTOSAR PduR section-10 containers are PduRRoutingPaths, PduRRoutingPath, PduRSrcPdu, and PduRDestPdu.

If Path A currently points to COM: that is a direct CanIf → COM route, not the secured receive route, unless the GUI is showing only global-PDU ownership. The decisive check is generated code: Path A must ultimately call SecOC_RxIndication; COM belongs on the separate post-verification Path B. See Lesson 5 — PduR Path A and Path B.

Primary source: AUTOSAR PDU Router R23-11, sections 10.2.6–10.2.9.

4. SecOC: configure the RX security object

SecOC's SecOCRxPduProcessing is the central per-PDU container. Configure one instance for HV_BATT and choose the single secured-PDU layer.

Freshness-related parameters: an important generator detail

Profile 2 has no freshness value, but the generic AUTOSAR RX container still exposes freshness-related parameters, including SecOCFreshnessValueId. Your Vector BSWMD may make some of them mandatory at ECUC level. Follow the DaVinci validator for multiplicity, but do not add a real freshness manager or a fake freshness value to the protocol. Set both lengths to zero, set SecOCUseAuthDataFreshness to false, and inspect generated code to confirm no non-zero freshness bytes enter DataToAuthenticator.

SecOC secured-PDU choice

  • Create SecOCRxSecuredPduLayer → SecOCRxSecuredPdu.
  • Set SecOCAuthPduHeaderLength = 0; there is no secured-PDU header in this contract.
  • Set SecOCSecuredRxPduVerification = TRUE.
  • Set SecOCRxSecuredLayerPduRef to HV_BATT_SecuredPdu.
  • Create SecOCRxAuthenticPduLayer and reference HV_BATT_AuthenticPdu.
  • Do not create SecOCRxSecuredPduCollection; that choice is for separate Authentic and Cryptographic PDUs.

Secured area

Preferred: omit SecOCRxPduSecuredArea. The AUTOSAR and local Vector BSWMD descriptions state that the complete Authentic PDU is then input to the authentication algorithm.

If your DaVinci release requires an explicit container, use:

SecOCSecuredRxPduOffset = 0 bytes
SecOCSecuredRxPduLength = 5 bytes

Never use length 3: that would exclude the two authenticated zero-padding bytes.

Primary source: AUTOSAR SecOC R23-11, sections 7.10.4 and 10.1.7–10.1.23; see also the HV_BATT mapping reference.

5. Csm: configure the MAC verification job

CSM separates the job interface from the cryptographic primitive. For this receiver, configure one MAC-verify primitive, one CSM job, a key reference, and a queue/channel appropriate for the RH850 crypto driver.

CSM MAC verification primitive

Create CsmPrimitives/CsmMacVerify/CsmMacVerifyConfig with:

CsmMacVerifyAlgorithmFamily          = CRYPTO_ALGOFAM_AES
CsmMacVerifyAlgorithmMode            = CRYPTO_ALGOMODE_CMAC
CsmMacVerifyAlgorithmSecondaryFamily = CRYPTO_ALGOFAM_NOT_SET
CsmMacVerifyAlgorithmKeyLength       = 16 bytes

The AUTOSAR CSM definition describes CsmMacVerifyCompareLength as the MAC-buffer length in bits for the synchronous RTE service interface, and CsmMacVerifyDataMaxLength as the data-buffer size for that interface. These are not automatically the same as the SecOC generated-function path. If your job uses CRYPTO_USE_FNC, do not invent these values solely from the presence of the parameter; follow the Vector validator and generated CSM configuration. If the active interface requires them, the values corresponding to this PDU are 24 bits for the compared MAC and 7 bytes for the maximum DataToAuthenticator input.

Primary source: AUTOSAR Crypto Service Manager R23-11, sections 10.2.4–10.2.5 and 10.2.17–10.2.18.

6. Crypto driver / ICUSE: complete the lower reference chain

The logical chain must be visible in the generated configuration:

SecOC SecOCRxAuthServiceConfigRef
  → CsmJob
      → CsmJobPrimitiveRef
          → CsmMacVerifyConfig
              → Crypto_30_CryWrapper primitive: AES-CMAC verify
                  → Crypto driver object / Cry_30_Rh850Icus
                      → CryCmacAes128VerConfig
                          → RH850 ICUSE

In the local Crypto wrapper BSWMD, the example primitive named AesCmacVerify uses CRYPTO_ALGOMODE_CMAC and CRYPTO_MAC_VERIFY, and its driver-object reference targets a CryCmacAes128VerConfig choice. Use the actual primitive and driver-object names available in your installed Vector/RH850 package.

ICUSE boundary. SecOC should not call ICUSE directly. If key loading, key IDs, workspace indices, or driver initialization differ in your RH850 package, the Cry/ICUSE Technical Reference and generated configuration take precedence over this generic map.

7. Scheduling and initialization

  1. Initialize the configured CAN driver and CanIf through the project's EcuM startup sequence.
  2. Initialize the crypto driver / CRY adapter and CSM using the generated startup sequence.
  3. Initialize PduR and SecOC.
  4. Schedule SecOC_MainFunctionRx at the configured SecOCMainFunctionPeriodRx.
  5. For asynchronous CSM/CRY, also schedule the generated CSM/crypto-driver main processing required by that package and enable the callback path.

R23-11 specifies the RX main-function period in SecOCMainFunctionRx/SecOCMainFunctionPeriodRx. The local Vector BSWMD additionally exposes SecOCPduProcessing = DEFERRED|IMMEDIATE and asynchronous CSM callback processing options. Do not choose asynchronous mode merely because ICUSE exists; choose it when the installed driver integration requires it.

8. Generated-code inspection: the first proof

After generation, search the generated output and record the actual symbols. The exact filenames vary by DaVinci release, but the following facts must be visible:

  • CanIf Rx PDU: CAN ID, Classical CAN type, DLC/data length 8, PduR upper-layer indication.
  • PduR: one CanIf → SecOC secured route and one SecOC Authentic → upper route.
  • SecOC RX table: AuthInfo length 24 bits, Data ID 0x0202, FV lengths 0, secured verification enabled, secured PDU length 8, Authentic PDU length 5.
  • SecOC generated verification path calls Csm_MacVerify with the authentication-layer/job ID, DataToAuthenticator pointer/length, received authenticator pointer, received authenticator length, and result pointer.
  • The generated DataToAuthenticator length is 7 bytes, and the data buffer contains the two Data ID bytes followed by all five Authentic PDU bytes.
  • CSM job resolves to AES + CMAC + MAC Verify + the intended key and queue.
  • Crypto wrapper/CRY resolves to the RH850 ICUSE AES-CMAC verification service.

The local Vector implementation provides a strong checkpoint: its RX verification code adds the RX Data ID, copies the full freshness value, selects the secured area, then calls Csm_MacVerify; after a successful result it forwards the Authentic PDU upward. This is the exact point where a wrong secured-area length or wrong Data ID becomes observable.

9. Small verification exercise

Without opening DaVinci, retrieve the configuration mentally:

Question: Which three values must be different between the physical secured PDU and the CMAC input?

Answer after thinking: physical length is 8, Authenticator is physically present in bytes 5–7 but absent from DataToAuthenticator, and DataToAuthenticator additionally contains the 2-byte Data ID.

Then validate four frames on the ECU or test bench:

  1. Valid payload, padding 00 00, valid MAC → Authentic PDU is forwarded.
  2. Change CAN byte 0, keep MAC → verification fails.
  3. Change CAN byte 3 or 4 from zero, keep MAC → verification fails because padding is authenticated.
  4. Change one MAC byte → verification fails and the Authentic PDU is not forwarded.
