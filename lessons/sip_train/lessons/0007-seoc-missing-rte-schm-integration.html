Lesson 07 · integration boundary

What the missing SecOC RTE and SchM files actually mean

If SecOC source and headers are copied into an existing project but the RTE is not generated by DaVinci, missing Rte_SecOC_Type.h, SchM_SecOC.h, and verification-status symbols are not isolated syntax problems. They are evidence that generated integration artifacts are missing.

Safety rule: Do not silence these diagnostics with arbitrary macros or empty functions until you have classified the symbol. Some are harmless generated adapters; others connect SecOC to scheduling, application status reporting, PduR, or the cryptographic result callback.

1. First classify the diagnostic

2. What Rte_SecOC_Type.h supplies

AUTOSAR CP R23-11 specifies several SecOC implementation types as available through Rte_SecOC_Type.h. The important one for your error is the verification result enumeration:

typedef uint8 SecOC_VerificationResultType;

#define SECOC_VERIFICATIONSUCCESS             0x00u
#define SECOC_VERIFICATIONFAILURE             0x01u
#define SECOC_FRESHNESSFAILURE                0x02u
#define SECOC_AUTHENTICATIONBUILDFAILURE     0x03u
#define SECOC_NO_VERIFICATION                 0x04u
#define SECOC_VERIFICATIONFAILURE_OVERWRITTEN 0x05u

The same type family includes:

typedef uint8 SecOC_FreshnessArrayType[SECOC_MAX_FRESHNESS_SIZE];

typedef struct
{
  uint16 freshnessValueID;
  SecOC_VerificationResultType verificationStatus;
  uint16 secOCDataId;
} SecOC_VerificationStatusType;

The member order above follows the R23-11 specification’s named elements, but the exact generated C declaration and memory-class qualifiers must match your AUTOSAR/RTE integration package. Treat the snippet as the semantic definition, not as permission to invent a vendor ABI.

Why a no-freshness PDU still needs the symbols: the SecOC module is compiled as a configurable generic implementation. Its source contains the freshness-failure path and the verification-status data type even when your configured HV_BATT PDU has SecOCFreshnessValueLength = 0. Configuration preprocessor switches may make the path inactive at runtime, but the required headers/types still have to be visible during compilation.

3. What SchM_SecOC.h supplies

SchM is the generated Schedule Manager integration boundary. It maps a module’s exclusive areas to the operating system, interrupt controller, or project lock implementation. This Vector SecOC delivery uses two exclusive-area contracts:

SchM_Enter_SecOC_SECOC_EXCLUSIVE_AREA_RXSTATE()
SchM_Exit_SecOC_SECOC_EXCLUSIVE_AREA_RXSTATE()

SchM_Enter_SecOC_SECOC_EXCLUSIVE_AREA_TXSTATE()
SchM_Exit_SecOC_SECOC_EXCLUSIVE_AREA_TXSTATE()

The local SecOC implementation enters RXSTATE around receive-state access and TXSTATE around transmit-state access. For example, the CSM RX callback enters RXSTATE before checking the callback state and exits it before immediate verification. These are not ordinary function calls that should be declared with an arbitrary return type; they are void-like synchronization macros.

A minimal shape for a project-owned mapping is:

#ifndef SCHM_SECOC_H
#define SCHM_SECOC_H

#include "SchM_YourOsOrInterruptLock.h"

#define SchM_Enter_SecOC_SECOC_EXCLUSIVE_AREA_RXSTATE() \\
  YourProject_Enter_SecOC_RxState()
#define SchM_Exit_SecOC_SECOC_EXCLUSIVE_AREA_RXSTATE() \\
  YourProject_Exit_SecOC_RxState()
#define SchM_Enter_SecOC_SECOC_EXCLUSIVE_AREA_TXSTATE() \\
  YourProject_Enter_SecOC_TxState()
#define SchM_Exit_SecOC_SECOC_EXCLUSIVE_AREA_TXSTATE() \\
  YourProject_Exit_SecOC_TxState()

#endif

For a single-threaded lab build, empty macros can remove the compile error, but they are only acceptable if you have proved that SecOC cannot be called concurrently from an ISR/task/CSM callback. Do not use empty macros in production without the project’s concurrency analysis.

4. The RTE verification-status function-pointer type

The local Vector source makes the missing RTE boundary visible in SecOC_Verify.c:

SecOCRteVerificationStatusType rteVerificationStatus =
  SecOC_GetRteVerificationStatusFuncTable(...);

if(rteVerificationStatus != NULL_PTR)
{
  (void)rteVerificationStatus(&verificationStatusStruct);
}

This means SecOCRteVerificationStatusType is a function-pointer typedef, and the generated SecOC configuration contains a table of callbacks. It is not the same thing as the AUTOSAR data type SecOC_VerificationStatusType.

Semantically, the callback is:

Std_ReturnType callback(
  const SecOC_VerificationStatusType *verificationStatus);

The actual Vector declaration must use the project’s P2FUNC, memory sections, and pointer-class macros. Obtain it from the matching generated SecOC_Lcfg.h/SecOC_Cfg_*.h output or the release’s RTE integration template. Do not typedef it as a plain void (*)(void).

5. Why the status symbols appear even if you do not need status reporting

The local implementation propagates three kinds of result:

SecOC_Verify_PropagateVerificationStatus(...)
SecOC_Verify_PropagateVerificationStatusWithSecuredPdu(...)
SecOC_Verify_PropagateClientServerVerificationStatus(...)

It writes a SecOC_VerificationStatusType and may call:

  • a configured C callout;
  • an RTE sender/receiver callback for the provided VerificationStatus port;
  • an RTE client/server callback for VerificationStatusNotification;
  • a secured-PDU status callout with the received secured PDU.

For your first HV_BATT receive test, decide explicitly:

RequirementConfiguration choiceIntegration consequence
Only authenticate and forward valid dataVerification-status propagation NONE; no calloutsNo application status callback is needed. The generated tables should contain null/no-entry values.
Application needs pass/fail statusPropagation FAILURE_ONLY or BOTHImplement the exact generated RTE/callout interface and link the receiver.
Security monitoring/IDS needs eventsEnable configured security event reportingProvide IdsM integration and event references; this is separate from the RTE status port.

Do not merely define SECOC_FRESHNESSFAILURE and leave an RTE callback pointer with the wrong prototype. A compile-clean callback ABI mismatch can corrupt the call at runtime.

6. The special case: SecOCQueryFreshness = CFUNC

Your contract has no freshness value. The local BSWMD provides SecOCQueryFreshness with CFUNC and RTE choices; AUTOSAR exposes the FreshnessManagement required port only for the RTE choice. For this RX-only Profile 2 setup:

  • set the query mode to CFUNC unless the project deliberately uses an RTE FreshnessManagement port;
  • do not create a fake freshness RTE port merely to satisfy a header include;
  • verify the generated configuration does not select SecOC_GetRxFreshness for this PDU when the freshness lengths are zero;
  • if the source still references freshness callout types, provide the generated type/configuration header, but do not return a fabricated freshness value.

The local source confirms that a configured C-function freshness path uses a function-table callback and that a failure is reported as SECOC_FRESHNESSFAILURE. That is a generic path; it does not change the active HV_BATT cryptographic contract.

7. Generated artifacts you must obtain or recreate

Copying only the component’s initial source/header folder is insufficient. The local SecOC make rules explicitly expect generated outputs:

GENERATED_SOURCE_FILES += $(GENDATA_DIR)\\SecOC_PBcfg.c \\
                          $(GENDATA_DIR)\\SecOC_Lcfg.c

include $(GENDATA_DIR)\\Make\\SecOC_rules_generated.mak

At minimum, inspect the DaVinci generation output for the matching release and bring these artifacts into the existing project’s generated include/source path:

  • SecOC_Lcfg.h and SecOC_Lcfg.c;
  • SecOC_PBcfg.c if post-build configuration is selected;
  • SecOC_Cfg_RxData.h and any other generated SecOC_Cfg_*.h files;
  • SchM_SecOC.h from the project’s SchM generation;
  • the RTE-generated Rte_SecOC_Type.h only if an RTE contract is actually enabled;
  • generated PduR/CanIf/Csm/Cry configuration and callback headers that match the same PDU/job IDs.
Version boundary: Your local implementation identifies itself as MICROSAR SecOC 19.02.06, while other local components may have different release numbers. Generated configuration, RTE types, SchM macros, and function-pointer prototypes must come from the same Vector package/release as the SecOC source. Mixing generated files from another release is not a safe fix.

8. Recommended resolution order

  1. Do not edit the vendor SecOC source to remove missing identifiers.
  2. Make sure the build uses the complete generated SecOC output directory before the initial component directory in its include order.
  3. Generate/copy SecOC_Lcfg.*, SecOC_Cfg_RxData.h, and the project’s SchM_SecOC.h.
  4. Decide whether verification-status propagation is NONE. If yes, remove the RTE status-port configuration and regenerate; if no, implement the generated callback prototypes exactly.
  5. Set SecOCQueryFreshness = CFUNC for this no-freshness design unless the project has a real RTE FreshnessManagement integration.
  6. Compile only after generated symbol errors are separated from genuine unresolved runtime dependencies.
  7. Then inspect the link map and generated code: Path A must call SecOC, SecOC must call CSM, and only successful verification must reach the Path B upper PDU.
