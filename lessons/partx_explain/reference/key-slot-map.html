Key Slot Map & Glossary

The compressed essence of Lesson 0001 — keep this beside you when reading the security stack or the DaVinci configuration.

1 · The four name layers

A single key travels under four different names. Everything else follows from this stack:

Layer 1 — Application alias · crypto_library_type.h:214–228 SECUREBOOT_KEY, JTAG_KEY, DATASTORE_KEY, INTEGRITY_KEY — roles invented by the project. Under KEYRAM_AS_KEY all four collapse onto KEY_RAM.
↓
Layer 2 — SHE enum · crypto_library_type.h:97–114 KEY_1…KEY_10, KEY_RAM, MASTER_ECU_KEY… — generic SHE slot names, values copied from the driver.
↓
Layer 3 — Raw KEY_ID · Cry_30_Rh850Icus_Types.h:67–82 CRY_KEYID_RAW_* numeric IDs (0x00–0x0E). These go into M1 byte 15 and into the ICUS0ICRCMD register.
↓
Layer 4 — Hardware · ICUSE manual §4.1, Table 4.1 Memory slots in the ICU region of the data flash; the RAM key lives in ICUSE-internal RAM. Key material is never readable from outside.

All six project keys are loaded with KU | WP (secure_boot.c:365,442): MAC-only use, frozen after first provisioning.

5 · The key update message M1–M5 (manual §4.4, Figure 4.1)

M1 (128 b) = UID(120) | ID(4) | AuthID(4)
M2 (256 b) = ENC_CBC,K1,IV=0 ( Counter(28) | KEY_FLAG(6) | "0…"94 | KEYID(128) )
M3 (128 b) = CMAC_K2 ( M1 | M2 )
M4 (256 b) = UID | ID | AuthID | ENC_ECB,K3 ( Counter | 1 | "0…"99 )
M5 (128 b) = CMAC_K4 ( M4 )

K1 = KDF(KEY_AuthID, KEY_UPDATE_ENC_C)     K3 = KDF(KEYID, KEY_UPDATE_ENC_C)
K2 = KDF(KEY_AuthID, KEY_UPDATE_MAC_C)     K4 = KDF(KEYID, KEY_UPDATE_MAC_C)

KEY_UPDATE_ENC_C = 01015348 45008000 00000000 000000B0h
KEY_UPDATE_MAC_C = 01025348 45008000 00000000 000000B0h
(extended keys KEY_11–20 use 0181…/0182… constants)
  • M1–M3 carry the registration; M4–M5 are the ICUSE's read-back proof that the key landed correctly.
  • Self-authenticated first load: when AuthID == ID and the auth key slot is unregistered, KEY_AuthID is treated as 0…0₁₂₈ — that is how this project provisions empty slots (secure_boot.c passes authKeyId = keyId, authKey = 0). [Manual §4.4, p. 43]
  • Counter is a monotonic 28-bit anti-replay value; must be ≥ 1 on first registration (project uses 1), 0 only for RAM_KEY.
  • UID wildcard = 120 zero bits; allowed only while the target key's DWC flag is 0.

8 · Glossary

ICUSE
ICU Security unit — the RH850 on-chip SHE-class security module performing AES128/CMAC/TRNG and secure boot.
ICU region
Part of the data flash reserved by ICUSE for key slots and their flags/counters; externally unreadable.
Memory slot
One key storage area in the ICU region (NVM keys) — addressed by KEY_ID.
KEY_ID
4-bit selector of a key slot (Table 4.1); appears in M1, in ICUS0ICRCMD[19:16], and in driver macros.
KEYMD
Bit 20 of ICUS0ICRCMD; selects the extended key page (KEY_11–20).
KEY_FLAG
6-bit attribute set stored with the key at registration: WP, BP, DP, KU, DWC, CU/VO.
AuthID
KEY_ID of the key that authenticates the update of another key; equals ID for self-authenticated first loads.
UID
120-bit device identifier read via CMD_GET_ID; all-zero value = wildcard (if DWC=0).
Counter (CID)
28-bit monotonic anti-replay counter stored with the key; updates require a strictly greater value.
M1–M5
SHE key-update messages: M1 (UID|ID|AuthID), M2 (encrypted key+flags+counter), M3 (authenticating CMAC), M4/M5 (ICUSE's verification proof).
K1–K4
Session keys derived via SHE KDF from the auth key (K1,K2) and the new key (K3,K4) with the KEY_UPDATE_*_C constants.
CMD_LOAD_KEY
ICUSE command 0008h — register/update an NVM key (or RAM_KEY) from M1–M3.
CMD_LOAD_PLAIN_KEY
ICUSE command registering a plaintext key into RAM_KEY (no M1M2M3 protection).
CMD_EXPORT_RAM_KEY
Exports RAM_KEY encrypted under SECRET_KEY for later re-import via CMD_LOAD_KEY.
RAM_KEY
Single volatile key in ICUSE-internal RAM; no KEY_FLAG, no counter; survives only until reset unless exported.
TRNG
True random number generator inside ICUSE; source of all key material in this project.
WP / one-way latch
Once WRITE_PROTECTION is set at registration, the slot is immutable until the next full chip erase.
