MPKA without Vector CSM/CryIf runtime sources

Pair with Lesson 0005. This defines what the project adapter must do; it does not say to link Vector Csm.c or CryIf.c.

Provider seam, not a registered callbackCrypto_30_CryWrapper_Hw_* are internal crypto-provider hooks reached through the wrapper's key-management functions. They are not automatically CSM/CryIf callbacks. A project-owned key facade must explicitly map handles and dispatch to those wrapper APIs (if linked), or to another approved provider implementation.
Two layers, one explicit seam Vector BSWMD, technical references, and public headers remain valuable for ECUC names, symbolic references, AUTOSAR argument semantics, and type contracts. Their runtime CSM/CryIf dispatcher sources are not a dependency in this integration. Provide a project-owned service facade/callback table, or use the Vector layer only where the SIP build already supplies it. Do not define duplicate global Csm_*, CryIf_*, or Crypto_* symbols alongside linked providers.

The project-local secoc_securitylib_csm_wrapper.c is a SecOC MAC adapter: it explicitly says it does not replace generated Csm.c and expects a project-specific dispatch hook. It handles MAC jobs, not MPKA key-management requests. Add a sibling MPKA key-operation adapter or a single facade that deliberately owns both; do not pretend this MAC wrapper already implements Csm_KeyExchangeCalcPubVal.

3 · If the Crypto wrapper remains the provider, keep its public service boundary

Crypto_30_CryWrapper_KeyManagement.c exposes public key APIs and forwards derive and key exchange to its Hw_* hooks. The current Hw.c has source implementations backed by the project's SecurityLib ECC extension. Prefer the public Crypto API/fixed wrapper dispatch route over calling Hw_* internals directly—unless your approved build intentionally uses those internal headers. In either case compile/link must prove a single active implementation.

  • Do not put fresh ECDH private scalars, peer shared values, or final MAC keys in Crypto element initial-value bytes.
  • MPKA externally sets the one-byte algorithm selector, custom member count/position, ECBD peer values and KDF fields; wrapper CalcPubVal internally creates PRIVKEY; wrapper CalcSecret/KDF internally write outputs via KeyElementSetInternal.
  • For MPKA, Crypto_30_CryWrapper_KeyElementSet and KeyValidSet are not synonymous: the first writes element content; the second marks all elements of that key valid (and may mark its NvM RAM block dirty).
  • Respect source-paired validity operations and failure return values. Do not mark a key valid after a failed partial write; do not let bitwise-OR of return statuses replace explicit first-error handling in new facade code.
  • The local CryptoWrapper's internal Csm types are Vector-specific and include RTE dependencies. Do not mechanically include/copy them into a new stand-alone facade without checking ownership, memory classes, licenses, and conflicting type definitions.

5 · Where job containers apply—and where they do not

The current MPKA source uses key-ID functions (Csm_KeyExchangeCalcPubVal, Csm_KeyExchangeCalcSecret, Csm_KeyDerive, element set/copy, key copy/validity). For those calls, a CsmJob/CsmPrimitive/CsmQueue/CryIfChannel chain is not the route shown by CSM runtime code; the CSM key maps to CryIf key and CryIf dispatches the key-management function table.

If the replacement only supports direct MPKA key APIs, implement those key callbacks; CsmJob ECUC references do not magically supply missing call routing. If SecOC or another BSW calls job-ID APIs like Csm_MacVerify(jobId,...), then configure/retain the separate job model as an interface contract or make a project job dispatcher:

Job clientSecOC CSM job handle → project job descriptor
↓
Job definitionCsmJobKeyRef → final CddMsgGrpKey; primitive → AES-CMAC; processing/callback contract
↓ if retaining the AUTOSAR/Vector routing model
Driver dispatchCsmQueue/CsmChannelRef → CryIfChannel/CryptoDriverObject → Crypto.ProcessJob

For a direct custom dispatcher, the equivalent job table must preserve job-ID whitelist, selected final key, MAC mode/data/MAC lengths, operation mode, result pointer, sync/async callback semantics, and error-vs-authentication-mismatch reporting. Do not create a second global Csm_MacVerify or Csm_MacGenerate if generated CSM is linked. This workspace's optional legacy adapter is synchronous, job-whitelisted and profile-specific; use it only as an explicit project hook, not as a generic crypto manager.

7 · Callback design rules for this implementation

  1. One owner per global symbol. Inventory symbols actually present in the IPC link. If the build already includes Csm_MacVerify, use a configured CSM job callout or a specifically owned dispatch seam. Do not add another global implementation beside it.
  2. Job whitelist. The MAC adapter accepts only registered generated TX/RX job IDs. A foreign or zero-but-present ID is not implicitly valid; encode job presence separately.
  3. Fail-closed lifecycle. Registration starts inactive. Only successful MPKA finalization plus verified key retrieval/load activates the MAC bridge. On failure, deactivation, wrong key length, or RAM_KEY update failure, keep it inactive.
  4. Preserve result taxonomy. A valid CMAC returns E_OK + CSM_E_VER_OK; a completed mismatch returns E_OK + CSM_E_VER_NOT_OK; invalid job, bad lengths, inactive key, or crypto hardware/service error returns E_NOT_OK.
  5. Do not recreate all CryIf lightly. A complete CryIf-like layer also owns module/function-table registration, per-key driver selection, key API validation, direct operation dispatch, copy semantics, error mapping and any cross-provider copy buffers. A name→CryptoKey lookup alone is not equivalent.
  6. Do not confuse callback replacement with provider replacement. Keep public wrapper services and key-element storage if the existing Crypto_30_CryWrapper module is still linked; replace only its documented/integration-approved callback seam. Calling private Hw hooks directly bypasses wrapper parameter checks and lifecycle serialization unless your design intentionally assumes those duties.

8 · Bring-up and verification gates

  1. Design artifact: inventory each MPKA CDD CSM key field and construct a table from symbolic key to facade handle to provider key handle to key type/element list. Document which real implementation owns each C API.
  2. Interface audit: compare exact Csm key service and Crypto_30_CryWrapper function prototypes, calling context, byte/bit units, return codes, read/write policy, and validity behavior. Align AUTOSAR release headers to the project. Do not expose generic RTE types unnecessarily in the reduced facade.
  3. Static provider audit: inspect call tree and build-source manifest for wrapper ECC/KDF functions, SecurityLib/mbedTLS sources, ICUS RNG service, and function-table/service entry. This lesson verifies source text only.
  4. Build PC: regenerate or hand-integrate through the approved process, compile with GHS, inspect duplicate symbols/unresolved externals, check stack/memory budgets and generated CSM/CryIf types. Current desktop cannot build this target.
  5. Target tests: initialize ICUS/PRNG and SecLib_Ecc; perform group-2 two-peer exchange; compare 16-byte KDF outputs only in a protected bench harness; check commit/copy/validity, cleanup, reset behavior, and SecOC key ownership; test wrong jobs/lengths/failure returns and valid/bad MAC outcomes. Never log ephemeral or derived secret bytes.

Short recall

Predict first, then choose for immediate feedback.

With no Vector CSM/CryIf runtime in the target, what do you take from their BSWMD?
Use the BSWMD and normative specs as configuration/interface references. The target implementation is project-owned unless a separately supplied licensed CSM/CryIf is actually present.
Where does this workspace's MPKA public-key operation land?
The observed Crypto_30_CryWrapper_Hw.c implementation calls SecLib_Ecc* for software P-224 math; SecLib_RandomGenerate reaches the ICUS RNG. Do not relabel software ECDH as ICUSE hardware ECC.
What happens if the job is configured but the custom dispatcher ignores jobId?
A project-owned MAC callback must enforce its registered job whitelist and resolve the associated final key. Merely receiving a numeric job ID does not automatically route through unavailable CSM/CryIf code.
