MPKA ECDH: Crypto–CryIf–CSM container map

Detailed reference to accompany Lesson 0004. It maps the BSWMD/configuration contract; it is not an ECUC export or an instruction to link Vector runtime sources. For the project-owned callback/facade architecture see the replacement map and Lesson 0005.

First decide which Crypto provider is in this build The local, current Crypto_30_CryWrapper_Hw.c implements ECDH and X9.63/SHA-256 by calling SecLib_Ecc*; that is CPU software math/KDF, not ICUSE ECDH. The mbedTLS/SecurityLib integration notes say the selected RNG bridge reaches the ICUS RNG. Keep those claims separate: “ICUSE performs cryptography” may be true for the RNG and other SHE AES operations, but it does not mean ICUSE calculates this ECDH. If the delivery/branch differs from these files, inspect the target build’s leaf implementation again.

1 · What this MPKA code actually dispatches

For this workspace, the MPKA state machine calls direct CSM key-management APIs, keyed by configured CsmKeyIds:

MPKA operationSource pathWhat to configure
Generate a public valueCsm_KeyExchangeCalcPubVal(keyId,...); MPKA expects curve-sized output.Group CSM key → CryIfKey → CryptoKey with exchange element layout; provider must implement the operation.
Compute peer/shared valueCsm_KeyExchangeCalcSecret(keyId, peer, len).Same group CSM/CryIf/Crypto key; provider reads the stored ephemeral private scalar and writes shared-value element.
Derive a SecOC message keyCsm_KeyDerive(kdfInputKeyId, tmpKeyId); source is in vKeyM_MPKA_DeriveMessageGroupKey.KDF-input CSM key and temporary-target CSM key each map to Crypto keys on the provider path; Crypto source and target must be driver-compatible.
Copy, clear, validateCsm_KeyElementSet/Copy, Csm_KeyCopy, Csm_KeySetValid.Access rights, matching element IDs/lengths, and CSM CSM_KEY support are required.

Important correction to generic container advice: MPKA is not calling Csm_JobKeyDerive or the CsmJob key-exchange APIs. The CSM runtime implementation gates these direct key APIs on CSM_KEY == STD_ON and forwards mapped CSM key IDs through CryIf. Configure the CsmKeys/CsmKey references as essential. Create CsmJobs/CsmPrimitives/CsmQueues only for other job-ID callers in this application (such as SecOC MAC verification, or a separate job-based random-generation client), not as substitute references for the MPKA key-ID calls.

2 · Step 0: freeze this IPC use case before opening DaVinci

  • Negotiation group ID: 2; IPC local member ID 3; EVCU remote member ID 4; two present members select runtime ECDH (per established project context).
  • Curve: the workspace software extension currently implements P-224/secp224r1; ensure CddKeyNegotiationCurve is secp224 and matches EVCU. BSWMD defaults are not proof of the active project setting.
  • Use case: SecOC key derivation, not MACsec. Do not create the MACsec-only second temporary key unless another configured group needs MACsec.
  • Keep CDD negotiation-group ID, local/remote member IDs, message-group ID, CSM key IDs, CryIf key/channel IDs, Crypto key/driver-object IDs, and SecOC Data ID separate. Assign project IDs in the appropriate component; no numeric value in a BSWMD is a project allocation.
  • Do not commit a 28-vs-56-byte shared value by intuition alone. The local MPKA BSWMD distinguishes x-only (28 B P-224) from X||Y (56 B) by CddKeyNegotiationSharedValueLengthType, and ties supported output to CS.00172 revision/use case. For this SecOC path, cross-check the approved CS.00172 revision and the implementation’s KDF vector/peer contract. Configure shared-value element and PASSWORD to the selected same length; both ECUs must use the same choice.

3 · CSM: configure key objects first

Configuration path from local CSM BSWMD: /AUTOSAR/EcucDefs/Csm/CsmKeys/CsmKey. Each CsmKey has a unique CsmKeyId, CsmKeyUsePort, and required CsmKeyRef to a CryIfKey.

Symbolic MPKA referenceCSM key roleWorkspace requirement/step
CddKeyNegotiationGroupKeyRefKEX_GROUP_2 (illustrative name only)One dedicated CSM key for negotiation group 2; do not reuse for another group; component BSWMD requires persistence. Key type/template must include the MPKA/provider-required ECBD-compatible and ECDH elements.
CddMsgGrpKDFInputKeyKDF_INPUT_2Source key for Csm_KeyDerive. PASSWORD capacity equals chosen shared-value length (P-224 28 or 56 B). SALT has at least 1 B for SecOC (source writes one message-group ID byte). It need not be persisted and may be shared across message groups only if concurrency/access policy permits.
CddMsgGrpTmpKeyMAC_TMP_2Target of X9.63/SHA-256 KDF; key element ID 1 is exactly 16 B per MPKA BSWMD; persistent; unique to one message group; compatible type with the final key for whole-key copy.
CddMsgGrpKeyMAC_FINAL_2Committed key, copied from temporary key after group success; same type; persistent; unique to message group; element ID 1 at least 16 B (16 B is the aligned AES-128 design).
  1. Create each CsmKey and assign a unique, project-owned CsmKeyId. Do not derive the numeric ID from the group/member ID.
  2. For each, set CsmKeyUsePort = FALSE unless an RTE key interface is actually required. MPKA calls BSW CSM APIs directly, not key client/server ports.
  3. Set CsmKeyRef to the corresponding CryIf key. CSM BSWMD explicitly says that its CsmKeyRef maps to CryIfKey, which then maps to a Crypto driver key.
  4. Enable and retain CSM_KEY runtime support in the configured release. If the feature is off, the inspected key-management implementation returns E_NOT_OK.
  5. Review CSM key-element set/copy/get and key-valid API availability/access against the installed version, generated header, and security policy. Do not make ephemeral private/shared-secret elements plaintext-readable just because the API exists.

4a · Access rights derived from observed call paths

  • External MPKA Csm_KeyElementSet calls need write access for the exact elements they set: algorithm selector; custom ECU position/count; both custom partner-public elements; overwrite/clear of shared value and private key; and derivation PASSWORD/SALT/clearing.
  • The wrapper’s private scalar is generated internally by the provider into the PRIVKEY Crypto element in CalcPubVal; MPKA later clears it. Do not seed it with a fixed value. The provider’s internal KeyElementSetInternal path is separate from external Csm write access, but keep policy consistent with the callout/clear APIs.
  • The wrapper reads its private scalar, PASSWORD, and SALT internally using a local Crypto-driver API; those internal reads do not imply public Csm_KeyElementGet must be enabled for those elements.
  • Csm_KeyElementCopy of the shared value to KDF PASSWORD and Csm_KeyCopy of the temporary key to the final key are same-driver internal copies in the inspected CryWrapper implementation. Avoid cross-driver mapping for the input/target keys unless the release’s cross-driver bridge, access policy, buffer capacity, and provider explicitly support it.
  • For the adapter in security/source/crypto_lib/secoc_securitylib_csm_wrapper.c, reading CddMsgGrpKey element 1 into a CPU buffer needs CSM/Crypto element read access; this is a compatibility adapter and CPU exposure. If you do not want that, keep it non-readable and bind the real SecOC CSM job directly to the final CSM key instead.

5 · CryIf: route keys and (only when relevant) jobs

Direct MPKA key-management operations

  1. Under CryIfKeys/CryIfKey, create one key mapping for each CSM key, with a unique CryIfKeyId and required CryIfKeyRef to its Crypto driver CryptoKey.
  2. Verify the CSM mapping chain is exactly CsmKeyRef → CryIfKey → CryIfKeyRef → CryptoKey. IDs are separate mapped domains; same numeric IDs are not required and should not be assumed.
  3. Add the referenced Crypto module under CryIfCryptoModules/CryIfCryptoModule and set CryIfCryptoModuleRef to the selected Crypto module configuration. This associates the module’s function table; it is distinct from the channel/key references.

Crypto channel only if a CSM job is configured

Direct Csm_KeyExchangeCalc*/Csm_KeyDerive key-ID APIs do not take a CSM job ID and do not dispatch through a CsmQueue/CryIfChannel. If you also configure a job-based API (e.g. a downstream SecOC MAC verify job or explicit random-generation job), add CryIfChannels/CryIfChannel with a unique CryIfChannelId and CryIfDriverObjectRef → CryptoDriverObject; reference that channel via the applicable CsmQueue/CsmChannelRef. Do not manufacture a queue merely to satisfy the direct MPKA key API. For mixed key storage across Crypto drivers, CryIf element/key copies may use a CPU buffer bridge, whereas CryIf key derivation dispatches to the source key’s driver and does not automatically bridge source/target drivers.

6 · Crypto: key types, keys, driver object, provider

  1. CryptoKeyElements: define each unique element ID and size/access/persist policy described above. The wrapper’s underlying implementation enforces exact length unless partial access is enabled; this directly affects PASSWORD, SALT, clearing writes, and temporary/final key copy.
  2. CryptoKeyTypes: create type layouts: a negotiation key compatible with the Vector KeyExchange_NISTP224R1_BD workflow, a KDF-input layout with PASSWORD/SALT, and a one-element 16-byte MAC-key layout used by temporary and final keys. Reference every required element definition in the key type.
  3. CryptoKeys: instantiate distinct CryptoKeys with unique CryptoKeyId, key-type reference, NVM binding/persistence according to the package and system design. Each CSM key’s CryIf mapping points to one of these.
  4. CryptoDriverObjects: create/use the Crypto driver object that owns the selected CryWrapper implementation. The CryIf Crypto channel, where job clients need one, points to it. This driver object BSWMD says no underlying driver queue is supported in this CryWrapper delivery; the queue field is only an async buffer with a 1-entry restriction. Do not use that as a recommendation to queue synchronous direct MPKA key APIs.
  5. CryptoPrimitive and provider support: configure a CSM CsmPrimitive / Crypto CryptoPrimitive tuple for key-exchange/KDF only if the configured API path consumes it. In the inspected direct key API path, operations dispatch by key to CryIf/Crypto function pointers rather than a configured CsmJob tuple. A symbolic AUTOSAR algorithm enum is not a provider implementation. At the provider layer confirm actual ECDH CalcPubVal, CalcSecret, X9.63-SHA256 derive, random source/ICUS call, correct P-224 encoding, feature macros, initialization, and matching generated code. This workspace’s wrapper functions are the actual software ECC implementation to trace; the top-level source note states the three former E_NOT_OK stubs were filled. Verify active branch/build PC includes it.

7 · Detailed work order in DaVinci

  1. Freeze release/provider scope. Record Vector CSM/CryIf/CryWrapper/ICUS versions, project AUTOSAR version, exact RH850 derivative/security option, CS.00172 revision, active config variant, and the Crypto provider selected by the build. BSWMD definitions are not the active ECUC values.
  2. Make a key inventory. For group 2 list KEX_GROUP_2; for its SecOC message group record KDF_INPUT_2, MAC_TMP_2, and MAC_FINAL_2. Those are illustrative container names only. Put each actual MPKA-generated key symbolic reference beside its CsmKey container and driver element type.
  3. Build key references bottom-up. Create Crypto element definitions → CryptoKeyTypes → CryptoKeys, map each with CryIfKey → CryptoKey, then set each CsmKey’s CsmKeyRef → CryIfKey. Finally set the MPKA CDD key references → those CsmKeys. Keep different ID domains distinct.
  4. Populate exact layouts. Use the 28/56/1/16-byte relationship table, but resolve shared-value length from project protocol revision and peer agreement. Check every MPKA set/copy/clear length against each destination element’s size/partial-access setting.
  5. Access and lifecycle. Set key-valid after each key population as the MPKA source does; ensure write permission for its key-element operations; provision NvM only where key persistence is required. Decide whether the final key is non-readable (prefer direct CSM jobs) or CPU-readable (only if the SecOcSecurityLib adapter is used and accepted).
  6. Add Crypto provider capabilities. Trace Crypto public key operation functions through to the actual selected leaf. On this project’s software ECC path, confirm P-224/ECDH/KDF works and that the initialized RNG bridge calls ICUSE. Do not use generic ICUS AES/RNG features as evidence of hardware ECC.
  7. Only add job containers for job callers. For CsmJob-based MAC verify/RNG: configure job ID, primitive ref + nested primitive service algorithm config, key ref, queue ref, sync/async/callback policy, queue channel ref, CryIf channel → driver object, and matching CryptoDriverObject primitive capability. For SecOC, job key should reference CddMsgGrpKey (final key) once generated configuration is integrated.
  8. Generate and audit on the IPC build PC. Review DaVinci consistency checks and generated CSM/CryIf/Crypto/MPKA tables. This current PC cannot run the configured GHS compiler or DaVinci validation; nothing in this lesson represents a successful generation/build/target test.
  9. Bench test on target. On two ECUs compare public-value contract and generated 16-byte derived-key equality using a protected test procedure; verify temporary-key copy, validity, cleanup, persistence/reboot behavior, and the SecOC job key binding. Do not log secret bytes.

Short recall

Answer from memory, then select an option for immediate feedback.

MPKA calls Csm_KeyExchangeCalcSecret(keyId, ...). What does keyId identify?
The direct MPKA API takes a CSM key ID. CSM maps that key through CsmKeyRef to CryIfKey, then CryIfKeyRef to the Crypto driver key. It is not a job or channel ID.
What must hold for CryIf direct KeyDerive?
CryIf dispatches KeyDerive through the source key's driver function table, passing both mapped CryptoKey IDs. Keep source and target on the same selected Crypto module/provider.
For a SecOC CSM_MAC_VERIFY job, which MPKA key belongs on its key reference?
After MPKA commits successfully, CddMsgGrpKey is the final message-group key. A SecOC CSM MAC job must reference that key, not the exchange key or temporary key.
