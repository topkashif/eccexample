Lesson 0003 · ICUSE Key Provisioning · ~12 minutes

From ECDH to KEY_5: landing a derived CMAC key in ICUSE

The one-sentence answer

The ECDH path derives the key — ephemeral P-224 keys → shared secret Z → X9.63/SHA-256 KDF → 16-byte AES-128 CMAC key — but as delivered it stops at software storage and RAM_KEY; to persist it in KEY_5 you must add one new step: wrap those 16 bytes in the SHE M1|M2|M3 update protocol (SecLib_KeySHEUpdate, keyId = 0x08) — the same machinery Lesson 0001 used for DATASTORE_KEY.

Generated vs. derived — the return of Lesson 0002's distinction DATASTORE_KEY was generated (TRNG). This key is derived: its value is a deterministic function of the ECDH shared secret plus the message-group ID. Both land in ICUSE the same way — M1|M2|M3 + CMD_LOAD_KEY — because once the 16 bytes exist, ICUSE doesn't care where they came from.

As delivered · notes §6 Key lives in software KeyStorage (TmpKey → Csm_KeyCopy → group key element) and, in Phase 2, is activated into the volatile RAM_KEY via SecLib_KeyRAMUpdate. Zero persistent slots — by design.

The KDF is textbook ANSI X9.63 (seclib_ecc.c:293): per 32-byte block, Si = SHA-256( Z ‖ counterBE32 ‖ SI ), counter starting at 1, blocks concatenated and truncated. SHA-256 runs in software (mbedtls), same as the ECP math — ICUSE has no ECC engine, and the notes record that as an agreed assurance deviation (private keys in zeroized CPU RAM, never in NVM or a protected slot).

The WP trap — the most important design decision here If the ECDH key rotates (renegotiation per the MPKA lifecycle), a WP-flagged KEY_5 can never be rewritten — ICUSE rejects the update with ERC_KEY_WRITE_PROTECTED. DATASTORE_KEY earns WP because its value never changes. A rotating ECDH-derived key must either stay in volatile RAM_KEY (the delivered design), be loaded without WP (rewritable, protected by the protocol instead), or accept slot-in-place freeze. Decide before the first provisioning — WP cannot be undone.

Two concrete integration gaps in the current tree

  1. The SecLib switch doesn't know KEY_5. SecLib_MACGenerate/SecLib_MACVerify whitelist slots: BOOT_MAC_KEY, SECUREBOOT_KEY, DATASTORE_KEY, INTEGRITY_KEY, KEY_RAM (crypto_library.c:238–246, 319–327). Using KEY_5 for CMAC hits default → "keyId not supported". Add case KEY_5: to both.
  2. Bridge the layers. The derived 16 bytes currently sit in a CryWrapper key element (software). To reach M1M2M3 you must read them out (e.g. SecLib_KeySHEUpdate called with a filled SecLib_KeyDataType, or a small new SecLib_StoreDerivedKeyInSHE(keyId, key16) in the security lib that composes Lesson-0001's flow) — mind the RAM_KEY ownership policy while doing so, and wipe the software copy after CMD_LOAD_KEY succeeds.

3 · Knowledge check

Q1 · On P-224, what are the private scalar and public point sizes?
seclib_ecc.h:37–39 — SECLIB_ECC_PRIVKEY_LEN 28, PUBKEY_LEN 56 (uncompressed X‖Y, big-endian). P-224 coordinates are 224 bits = 28 bytes.
Q2 · Which KDF turns the shared secret into the CMAC key?
seclib_ecc.c:293 — Si = SHA-256(Z ‖ counterBE32 ‖ SI), SI = 1-byte message-group ID; output truncated to 16 B. The SHE KDF (Lesson 0001) is a different function, used only for M1M2M3 transport keys.
Q3 · How do the derived 16 bytes get into KEY_5?
Persistent slots only accept the SHE update protocol: SecLib_GenerateM1M2M3 + SecLib_KeySHEUpdate → CMD_LOAD_KEY (Lesson 0001). PLAIN_KEY is RAM_KEY-only; KeyElementSet is software storage; M4M5 is the read-back proof, not a write path.
Q4 · Why is setting WP on KEY_5 dangerous for a rotating key?
WP is a one-way latch (manual §4.3): the slot can never be rewritten or erased. The next ECDH negotiation produces a new key that KEY_5 would refuse — ERC_KEY_WRITE_PROTECTED.
