Lesson 0005 · AUTOSAR interface replacement · RH850F1K / ICUSE · ~8 minutes

Keep the MPKA key contract; replace the dispatch layer

One tangible win: sort each MPKA request into the runtime service your project must supply—and keep AUTOSAR container configuration separate from unavailable Vector CSM/CryIf implementation code.

Your mission The IPC target must not depend on Vector SIP CSM or CryIf source implementations. It already has a project Crypto_30_CryWrapper provider, SecurityLib ECDH/KDF and ICUS AES/RNG paths. We will identify a clean seam between MPKA's CSM-shaped requests, the project's key mapping/storage, the provider callbacks, and the optional SecOC MAC bridge.

A complete CryIf replacement does more than rename keys: it registers crypto modules/function tables, maps key handles to each provider, dispatches direct key-management functions, validates IDs and errors, defines same-/cross-provider copy semantics, and owns concurrency. If this IPC integration has one provider and a narrow MPKA scope, a smaller MPKA-facing key-service facade may be safer than silently recreating every CSM/CryIf API. Keep a project namespace (for example SecStack_*) unless unmodified MPKA formally requires the exact Csm symbols and no competing owner is linked. The Crypto_30_CryWrapper_Hw_* functions are internal crypto-provider hooks, not callbacks automatically registered with CSM or CryIf; your facade must explicitly call the wrapper's public key-management entry points (when those are in the target), or own the approved alternative route.

4 · Configure the key model—not a fictitious job path

  1. Allocate symbolic roles. Group 2 gets one group-exchange key; its SecOC message-group reference gets a KDF-input key, a temporary key and a final key. Names like KEX_GROUP_2 and MAC_FINAL_2 below are examples, not configured project names.
  2. Design the map. If you retain Vector BSWMD/DaVinci as an offline design/reference model, create CsmKeys/CsmKey entries pointing by CsmKeyRef to CryIfKey; map each CryIf key by CryIfKeyRef to a CryptoKey; create wrapper CryptoKeyTypes/element sets. In the target, reproduce these relationships in your own generated/static project descriptor table, if that is your approved integration path.
  3. Configure the four roles independently. Group exchange: `OWNPUBKEY` 56 B, `PRIVKEY` 28 B, `SHAREDVALUE` configured length, algorithm byte and the Vector ECBD workflow fields. KDF input: PASSWORD capacity matches SHAREDVALUE (or uses explicit partial-write semantics), SALT at least 1 B for SecOC's one-byte message-group ID. Temp and final SecOC keys: key element ID 1 is 16 B, compatible types; final key is the committed SecOC key.
  4. Keep access narrow. MPKA's Csm element-set/clear calls need writes for the elements they modify. The wrapper internally reads PRIVKEY/PASSWORD/SALT; that does not imply an external KeyElementGet permission. Only make final key readable if the selected CPU-copy adapter is accepted; direct job-to-final-key use can keep it non-readable.
  5. Set validity/lifecycle deliberately. Mirror MPKA's Csm_KeySetValid ordering. Its state machine calls Csm_KeyCopy(tmp, final) only on successful negotiation/derivation, then clears temp and validates final. Persistence must be backed by the selected storage/NvM implementation, not the word “Persist” alone.
  6. Keep IDs distinct. MPKA negotiation group 2, local member 3, remote 4, message-group ID, CSM key handle, CryIf key ID, CryptoKey ID, driver-object/channel ID, and SecOC job ID are different namespaces. Resolve references, don't alias integers by habit.

ECDH contract: P-224 private scalar = 28 bytes; public point = X||Y = 56 bytes; KDF shared input = 28-byte x or 56-byte x||y per the agreed MPKA/CS.00172 contract. SecOC KDF salt is 1 byte; temporary output is 16-byte AES-128 key. Confirm shared length is the same on IPC/EVCU and matches the approved spec revision. Vector's numeric IDs for custom CRYPTO_KE_CUSTOM_KEYEXCHANGE_* are not in the checked-in CSM headers; resolve them from the exact licensed template/generated types, never guess.

5 · Add jobs only for actual job-based consumers

MPKA's current source calls direct Csm_Key* key-management APIs, not Csm_JobKeyExchange… or Csm_JobKeyDerive. Thus CsmJobs/CsmJob, CsmPrimitives, CsmQueues/CsmQueue, CryIfChannels/CryIfChannel, and CryptoDriverObjects are not the MPKA key-ID route.

SecOC's Csm_MacVerify(jobId,…) is different. If generated Vector CSM remains on target for the job path, configure its MAC job, primitive, key, queue, channel and driver object normally; bind the job's key to MPKA's committed CddMsgGrpKey. If that dispatcher also is absent, implement a separate project job-ID registry/dispatcher preserving the interface contract. The existing SecurityLib MAC adapter requires an explicit hook; its file says it does not replace CSM globally. Never map every job ID to KEY_RAM or ignore jobId.

6 · Two deliberate routing choices for SecOC

Option A: direct Crypto-key/job pathOption B: existing ICUS adapter
Retain a supplied CSM job runtime if present. Job key maps to the MPKA final key. Avoid reading key bytes into application memory. Configure Crypto MAC primitive/provider and actual callback/sync policy.After successful MPKA finalization, read exact 16-byte final key via Csm_KeyElementGet, load dedicated ICUS KEY_RAM via SecLib_KeyRAMUpdate, then activate only registered SecOC jobs. This exposes key bytes to CPU RAM and needs final-key read access plus exclusive KEY_RAM ownership. It is compatibility, not an opaque HSM key transfer.

For the lesson's referenced Profile 2 contract: input to MAC = 2-byte Data ID || 5-byte Authentic PDU = 7 bytes; key = 16 bytes; received MAC = 3 bytes = 24 bits at CSM MacVerify. The legacy SecurityLib verifier consumes byte length, so pass 3 bytes; a completed comparison mismatch returns E_OK + CSM_E_VER_NOT_OK, not a CSM service-failure code. Do not pass a 16-byte result into a 3-byte SecOC buffer.

Knowledge check

Which part is not a job-container configuration for MPKA's current calls?
MPKA directly calls key-ID functions. Configure the key mappings/storage/provider callbacks. A CsmJob/CsmQueue applies only when a real caller uses a job-ID service, such as SecOC MAC verify.
What does the current wrapper do for P-224 ECDH math?
Crypto_30_CryWrapper_Hw.c calls SecLib_Ecc* software ECP functions. The RNG bridge calls ICUS. Don't call this hardware ECDH.
What must a job dispatcher use to select the configured SecOC MAC key?
A Csm_MacVerify job ID resolves to its configured job record and final-key handle. Whitelist only known job IDs; do not hard-code one key for unrelated CSM clients.
