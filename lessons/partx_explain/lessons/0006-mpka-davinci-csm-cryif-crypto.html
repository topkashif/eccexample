Lesson 0006 · DaVinci configuration work order · RH850F1K / ICUSE · ~10 minutes

Configure Csm, CryIf and Crypto so MPKA's four key references resolve

One tangible win: you can open DaVinci and enter the complete Csm → CryIf → Crypto container chain that turns MPKA's four CDD key references into four working key objects — and know exactly which parts the security folder must implement instead of linking.

Your mission The IPC runs MPKA group 2 (IPC member 3, EVCU member 4 → ECDH, P-224) but does not link Vector's Csm/CryIf runtime. The Csm and CryIf containers are still configured in DaVinci: they make MPKA's references resolvable and generate the ID headers your custom implementation must agree with. The runtime behavior comes from the security folder. This lesson walks the containers bottom-up and names the traps.

1 · The four references, and why containers still matter

MPKA's BSWMD requires exactly four Csm key references per SecOC use case:

MPKA parameterRoleExample CsmKey
CddKeyNegotiationGroupKeyRefnegotiation key: private scalar, public points, shared valueCSM_KEX_GROUP_2
CddMsgGrpKDFInputKeyX9.63 input: PASSWORD (shared value) + SALT (msg-group ID)CSM_KDF_INPUT_2
CddMsgGrpTmpKeyreceives the derived 16-byte AES keyCSM_MAC_TMP_2
CddMsgGrpKeycommitted key SecOC ultimately consumesCSM_MAC_FINAL_2

Configuring the containers produces three things even with a custom runtime: DaVinci validates the whole reference graph; the generator emits the key/element ID macros (Csm_Cfg.h, Crypto_30_CryWrapper_Cfg.h) that MPKA and your facade compile against; and the ECUC export documents the agreed key model. What you do not get from DaVinci is runtime behavior — one owner per Csm_*/CryIf_* symbol at link time, which is the security folder's implementation.

2 · The chain DaVinci makes you build

MPKA (Cdd module)CddKeyNegotiationGroupKeyRef, CddMsgGrpKDFInputKey, CddMsgGrpTmpKey, CddMsgGrpKey → CsmKeys/CsmKey
↓ each CsmKey: CsmKeyId + CsmKeyRef → CryIfKey
CryIfCryIfKey: CryIfKeyId + CryIfKeyRef → CryptoKey; channels map queues → driver objects; the CryptoModule container binds the provider
↓ each CryptoKey: CryptoKeyId + CryptoKeyTypeRef → key type → elements
Crypto (CryWrapper)key elements with IDs = the CRYPTO_KE_* macros · driver object · provider = SecLib_Ecc/mbedtls ECP + ICUS RNG — software ECDH, not ICUSE ECC

Three different key-ID namespaces (Csm, CryIf, Crypto) plus a fourth (element IDs) — never assume they share numbers.

3 · The traps, container by container

  1. CryptoKeyElement IDs must equal the compiled CRYPTO_KE_* macros. The wrapper searches elements by ID: PRIVKEY 9, OWNPUBKEY 10, SHAREDVALUE 1, ALGORITHM 12, PASSWORD 1, SALT 13. The custom ECBD elements (PARTNER_PUB_KEY, PARTNER_PUB_KEY_2, INTERMEDIATE, ECU_ID, NUM_ECU) take their IDs from the licensed delivery — MPKA writes them unconditionally in the cancel path, so the key type needs them even for ECDH.
  2. The SHAREDVALUE element size is not just capacity — it selects the encoding. 28 bytes → x-only, 56 → x||y, per the wrapper's CalcSecret. It must equal the group's CddKeyNegotiationSharedValueLengthType and EVCU's choice.
  3. CryIfMaxSizeOfKeyElement defaults to 32 — raise it to ≥ 64. CryIf sizes its internal copy buffers from this parameter; 56-byte public values fail silently at 32.
  4. Do not configure key-exchange or KDF jobs for MPKA. Its state machine calls direct key-ID APIs (Csm_KeyExchangeCalcPubVal/CalcSecret, Csm_KeyDerive, element set/copy, Csm_KeyCopy). Jobs exist only where a job-ID client exists: SecOC's Csm_MacGenerate/Csm_MacVerify (AES/CMAC, 7-byte input, 3-byte MAC) routed via a CsmQueue → CryIfChannel → driver object.
  5. Validity is separate from content. MPKA pairs every write/copy with Csm_KeySetValid; access flags stay narrow (private/shared/password elements RA_DENIED; final key readable only if the KEY_RAM adapter path is the approved choice).

Full parameter-by-parameter entry values, the audit checklist, and the build-PC/target validation gates are in the work-order reference below.

Knowledge check

Which single element-size setting also selects the ECDH shared-value encoding?
The wrapper branches on the configured SHAREDVALUE element length: 28 → x-only, 56 → x||y. It must match CddKeyNegotiationSharedValueLengthType and EVCU.
Why configure Csm/CryIf containers when their runtime is custom?
Containers make MPKA's CDD refs resolvable, validate the graph, and emit the Cfg headers your facade compiles against. Runtime behavior is the security folder's.
Which CryIfGeneral parameter silently breaks 56-byte key-element copies at its default?
Internal copy buffers are sized from CryIfMaxSizeOfKeyElement; the default 32 is smaller than a 56-byte public value. Set ≥ 64.
What does MPKA's state machine actually call for key agreement and derivation?
Csm_KeyExchangeCalcPubVal/CalcSecret, Csm_KeyDerive, element set/copy and Csm_KeyCopy with key IDs — no keyx/KDF jobs. Jobs are only for SecOC MAC services.
