Configure MPKA’s CSM key path

One tangible win: translate the MPKA ECDH calls into the right CSM keys, CryIf key maps, and Crypto key layouts—without mistaking a job ID for a key ID.

Mission connection Your IPC has a two-present-member MPKA group (group ID 2, IPC member 3, EVCU member 4). The negotiated result becomes a SecOC message-group key. Our goal is to configure its references and key lifecycle, not to claim a generated or target-tested ECUC configuration.

1 · Begin at the call sites

In the supplied vKeyM_MPKA_CryptoStateMachine.c, MPKA invokes the direct key-ID CSM APIs:

  • Csm_KeyExchangeCalcPubVal(keyId, ...) — public point, around line 598.
  • Csm_KeyExchangeCalcSecret(keyId, peerPoint, length) — shared value, around lines 492/537.
  • Csm_KeyDerive(sourceKeyId, targetKeyId) — KDF input to temporary key, line 1050.
  • Csm_KeyElementSet/Copy, Csm_KeyCopy, Csm_KeySetValid — prepare, clear, commit, and validate key material.

These calls take CSM key IDs, not CsmJob IDs. The CSM source forwards them to CryIf, which maps the key to Crypto. A CsmJob/CsmQueue/CryIfChannel chain is a separate route for job-ID APIs such as Csm_MacVerify; it is not a prerequisite for the MPKA direct key calls. In this MICROSAR CSM source, direct key APIs are compiled under CSM_KEY == STD_ON; confirm that feature is enabled in the actual integration.

2 · Create the four CSM key objects

Use CsmKeys/CsmKey. The CSM key is a handle/reference; its element layout lives in the Crypto key type.

MPKA CDD referenceRoleConfigure
CddKeyNegotiationGroupKeyRefECDH group keyOne dedicated persistent key per negotiation group; use the Vector ECBD-compatible key template even though two present members choose ECDH at runtime.
CddMsgGrpKDFInputKeyKDF sourcePASSWORD holds the shared value; SALT holds the one-byte SecOC message-group ID. Not persistent; the component allows reuse only subject to safe concurrency.
CddMsgGrpTmpKeyTemporary derived keyCrypto element ID 1, 16 bytes for this AES-128 SecOC key; persistent and unique to the message group.
CddMsgGrpKeyCommitted final keySame key type as the temporary key; element 1 at least 16 bytes (use 16 for the AES-128 contract); persistent and unique to the message group.
  1. Create each CsmKey and assign its own project-unique CsmKeyId. Do not reuse group ID 2, member ID 3/4, or message-group ID as the CSM key ID.
  2. Set CsmKeyUsePort = FALSE unless a real RTE key port is needed. MPKA calls CSM BSW APIs.
  3. Set required CsmKeyRef to a CryIfKey. CSM BSWMD specifies this target; CryIf then points to the Crypto key.
  4. Keep the group-exchange key, KDF-input key, temporary key, and final key as separate logical keys. For this CryWrapper key-derive/copy path, map all four to the same Crypto driver/module; CryIf dispatches KeyDerive using the source key’s driver function table.

3 · Configure Crypto element layouts

For P-224, the local MPKA reference specifies a 28-byte private scalar and 56-byte wire public point (X||Y). The configured shared value is either 28 bytes (x) or 56 bytes (x||y); its length must agree with CddKeyNegotiationSharedValueLengthType, the peer, and the approved CS.00172 revision. The local project integration notes select 56 bytes for the SecOC requirement they implement; do not apply that choice to a different specification revision without review.

Crypto keyElements and size guidance
Group exchangeCRYPTO_KE_KEYEXCHANGE_PRIVKEY (ID 9): 28 B; ...OWNPUBKEY (ID 10): 56 B; ...SHAREDVALUE (ID 1): selected 28 or 56 B; ...ALGORITHM (ID 12): 1 B. The Vector template also has custom ECU-count/local-position and ECBD partner/intermediate elements; their write access and curve-sized capacities must match the delivered MPKA template.
KDF inputCRYPTO_KE_KEYDERIVATION_PASSWORD (ID 1): shared-value length; CRYPTO_KE_KEYDERIVATION_SALT (ID 13): at least 1 B for SecOC. MPKA writes the message-group ID as one byte.
Temporary + final SecOC keyKey element ID 1: 16 B. Use compatible key types because MPKA commits by copying the temporary key to the final key.

In CryptoKeyElements/CryptoKeyElement, set the element ID, maximum size in bytes, partial access, persistence, read access, and write access. Then assemble CryptoKeyTypes/CryptoKeyType with its element references, and instantiate CryptoKeys/CryptoKey with a unique CryptoKeyId and type reference. Link each CryptoKey through CryIf and CSM.

Element IDs: the standard exchange/KDF element IDs above are in the supplied Crypto_GeneralTypes.h. MPKA also uses Vector custom CRYPTO_KE_CUSTOM_KEYEXCHANGE_* element names. Their numeric definitions are not present in the CSM headers checked into this workspace; obtain them from the exact delivered Vector key template/generated type definitions. Do not guess them.

4 · Choose access and persistence from the calls

  • MPKA externally sets and later clears algorithm/control fields, partner-public elements, PRIVATEKEY, SHAREDVALUE, PASSWORD, SALT, and the temporary/final key element. Their active Crypto write policy must permit these CSM writes; exact wrapper access checks must be confirmed in the selected release.
  • The software provider internally reads the private scalar, PASSWORD, and SALT. That is not a requirement to expose those values through public Csm_KeyElementGet. Keep external plaintext reads denied unless a specific consumer requires them.
  • If you use SecOcSecurityLib_ActivateMessageGroupKey, it reads final key element 1 into CPU RAM and then loads ICUS RAM_KEY; this needs readable final-key access and creates plaintext exposure. Otherwise, keep the final key non-readable and bind the SecOC MAC job directly to CddMsgGrpKey.
  • MPKA BSWMD requires persisted group, temporary, and final keys; the KDF-input key need not be persisted. The Crypto persist flag alone does not prove restart persistence—confirm the delivery’s NvM/key-storage binding and reset behavior.

5 · CryIf mapping

  • CryIfKeys/CryIfKey: one unique CryIfKeyId and CryIfKeyRef → CryptoKey for each MPKA key.
  • CryIfCryptoModules/CryIfCryptoModule: reference the actual configured Crypto module with CryIfCryptoModuleRef.
  • CryIfChannels/CryIfChannel: configure CryIfChannelId and CryIfDriverObjectRef only for job/queue clients. It is not part of direct MPKA CSM key-ID dispatch.
  • Keep all MPKA KDF source/target keys and keys involved in the commit copy on the same Crypto provider/module. CryIf KeyDerive routes through the source key’s Crypto function table; it does not do a cross-driver KDF bridge.

6 · Keep CsmJobs / CryptoPrimitives in their lane

Do not create CsmJobKeyExchangeCalcPubVal, CsmJobKeyExchangeCalcSecret, or CsmJobKeyDerive just because their containers appear in CSM BSWMD. Those configurations apply only if a caller uses the corresponding Csm_Job… API. For a real job-ID caller, configure CsmJobs/CsmJob with job ID, CsmJobKeyRef, CsmJobPrimitiveRef, CsmJobQueueRef, and the required processing/callback settings; the CsmQueue references a CryIfChannel and the CryptoDriverObject references matching CryptoPrimitive capabilities.

The local CryptoWrapper CryptoPrimitiveService capability list describes job services such as MAC, hash, encrypt/decrypt, and random; it is not a place to invent a direct key-exchange service tuple. The direct exchange/derive APIs dispatch by mapped key IDs to the provider’s key-management functions. If adding a separate SecOC Csm_MacVerify(jobId,...), that MAC verification service does need its own CSM job/primitive/queue path, and its job key should be the committed final MPKA message key.

7 · Check the provider and project values

  • The MPKA BSWMD provides CddCryptoKeyExchangeAlgorithmValueSECP224ECDH and says the one-byte selector is defined by the selected Crypto driver. Use the installed package/provider value, not a generic CSM algorithm-family enumeration or a guessed byte.
  • The checked-in wrapper at Crypto_30_CryWrapper_Hw.c:880–1102 calls the software SecLib_Ecc* provider for P-224 public generation, ECDH secret, and X9.63/SHA-256 KDF. This is not proof that ICUSE performs ECC, nor proof the active GHS build includes these files.
  • MPKA’s CSM APIs are guarded by CSM_KEY == STD_ON in this CSM source. The inspected Csm BSWMD does not expose a simple ECUC toggle with that name; confirm feature generation/configuration in the actual delivery.

8 · Verification handoff (current PC cannot build)

  1. On the IPC build PC, inspect active project ECUC and generated IDs; do not treat this component BSWMD as the ECU’s final config.
  2. Check every MPKA CDD key ref → CSM CsmKey → CryIf key → CryptoKey → CryptoKeyType → required element.
  3. Check ECDH selector value, curve, shared-value length, PASSWORD capacity/partial access, SALT size, target ID 1 size, key type equality for commit copy, persist and read/write policy.
  4. Confirm direct key APIs compile into CSM and the selected Crypto driver’s three provider operations are included, initialized, and target compatible. Run DaVinci validation and GHS build there.
  5. On RH850 test two-peer public point exchange, equal KDF result without logging secrets, temporary→final commit/validity, cleanup, reset persistence, and the actual SecOC final-key binding.
